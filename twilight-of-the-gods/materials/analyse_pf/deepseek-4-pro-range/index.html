    Planner Graph Refactor Proposals: Evaluation & Ranking¶

    Evaluator: Sisyphus (DeepSeek-v4-pro) Date: 2026-06-08 Baseline: current-graph.md, agent.py:846-2190

    Executive Summary¶

    All 10 proposals diagnose the same problem: plan_node() (347 lines, lines 846–1192) is a monolithic function that hides the planner's actual control flow inside a single LangGraph node. The Mermaid diagram in current-graph.md shows plan -> [5 action nodes], but the real policy — iteration gates, bootstrap questions, schema preparation, calculator lifecycle management, LLM invocation, post-LLM decision correction — is invisible at the graph level.

    Universal agreement across proposals: - Deterministic policy decisions should be graph-level nodes + conditional edges, not if blocks inside a 350-line function. - The LLM call should be isolated in a thin node that only asks the model for a decision. - Loop-back edges should re-enter through a canonical iteration-entry node (not directly to the planner). - route_after_plan should regain routing intelligence.

    Key areas of divergence: 1. Granularity — how many nodes to create (2 vs. 4 vs. 10 vs. 14+) 2. Corrector chain placement — post-LLM rewrites as nodes, as one node, or in edge functions 3. Bootstrap question nodes — dedicated ask_region/ask_currency nodes vs. inline in a guard node 4. Transient state — _route / _pre_check_route sentinel fields vs. routing purely from decision fields 5. Migration strategy — helper extraction first vs. direct graph surgery

    Proposal Rankings¶

    Tier 1 — Comprehensive, Well-Argued, Practical¶

    #1: DeepSeek-4-Pro (deepseek-4-pro-proposal.md) ★★★★★¶

    Approach: 4-node pipeline: guard → prepare → plan → adjust

    Aspect Assessment
    Problem diagnosis Excellent. Line-level mapping of all 12 concerns in plan_node with location references.
    Design clarity The adjust node as a pure post-LLM transformation is the proposal's strongest insight — it creates a single canonical "decision normalization" stage that both LLM and deterministic decisions pass through.
    Migration plan Best in class. Four explicit phases with test verification gates at each step. Phase 1 (extract helpers without graph changes) is risk-free and immediately proves correctness.
    Trade-off analysis Thorough. Explicit disadvantages table with mitigations. Risk assessment with severity ratings.
    Code examples Concrete edge definitions, routing function signatures, node responsibility tables.
    Open questions Three alternatives considered and rejected, each with clear reasoning.

    Strengths: - The prepare → adjust pipeline architecture where auto-complete and acquisition task decisions route through adjust (rather than directly to action nodes) is a non-obvious design choice that prevents duplication of _adjust_calculation_decision logic. This shows deep understanding of the existing code's coupling. - recipes in state is a practical cache that eliminates redundant build_dynamic_recipes calls across nodes. - plan → plan self-loop for decomposition re-prompt is elegant: the LLM gets a second chance with updated recipes without complex graph topology. - The guard node correctly serves as the canonical loop-entry point for all action nodes, replacing the current plan re-entry pattern.

    Weaknesses: - guard mixes iteration counting with region/currency checks — a slightly cleaner split (per GPT-5.4's tick + bootstrap_gate) would improve test isolation. - recipes in state requires serialization verification; FieldAcquisition objects may carry non-serializable fields.

    Verdict: Best balance of decomposition depth vs. graph complexity. The 4-node pipeline is the "Goldilocks" solution — enough decomposition to make the graph honest, not so much that it becomes noise.

    #2: GPT-5.4 (gpt-5.4-proposal.md) ★★★★½¶

    Approach: 6-node pipeline: tick → bootstrap_gate → prepare_context → acquisition_gate → llm_plan → decision_policy

    Aspect Assessment
    Problem diagnosis Clear and concise. Focuses on the right problem (hidden orchestration).
    Design clarity Exceptional. The stated design rule — "deterministic orchestration belongs in graph phases; business logic stays in helpers; LLM planning stays small" — is the single best articulation of what all proposals are trying to achieve.
    Migration plan Six-stage migration, each independently shippable. Explicit about what should NOT change (ask_user remains only interrupt, thread namespacing unchanged, outer runner contract preserved).
    Trade-off analysis Anti-patterns section is uniquely valuable: "Do not move state mutation into edge functions", "Do not increment iterations in every gate", "Do not turn every policy rule into a node". These constraints are more important than the specific node split.
    Code examples None (design-level only).
    Open questions None explicit.

    Strengths: - The separation of tick (iteration lifecycle only) from bootstrap_gate (region/currency questions) is a cleaner decomposition than DeepSeek-4-Pro's combined guard. - The explicit anti-pattern warnings are gold — they prevent the refactor from creating new problems. - "One decision_policy node is enough" — correctly rejects the over-splitting temptation seen in Opus and Qwen-3.7. - Stage-by-stage migration with "only after behavior is stable should tests be renamed" shows production discipline.

    Weaknesses: - No code examples or concrete routing function signatures. Remains at the design level. - acquisition_gate merging calculator cap/success checks with acquisition task selection conflates two concerns that DeepSeek keeps separate (prepare for calc lifecycle, adjust for decision routing). - Doesn't address the recipes caching problem that DeepSeek-4-Pro identifies.

    Verdict: The best design principles document. Should be read alongside any implementation — its anti-patterns and migration discipline are universally applicable. Loses to DeepSeek-4-Pro on concrete implementation guidance.

    #3: Opus (opus-proposal.md) ★★★★½¶

    Approach: Maximal decomposition: 14+ nodes in a g_* (gate) → enrich → acquire → plan_llm → c_* (corrector chain) → dispatch topology.

    Aspect Assessment
    Problem diagnosis Most thorough line-level mapping. 17 concerns enumerated with exact line ranges and categories (guard / deterministic ask / enrichment / corrector / side-effect).
    Design clarity The g_* / c_* naming convention is excellent — it makes the graph self-documenting. The dispatch node as canonical decision-log + route point is the right abstraction.
    Migration plan Three-step (extract helpers → hoist gates → split correctors), each with explicit risk assessment.
    Trade-off analysis Detailed. Explicit about checkpointer write cost of 10+ node hops per iteration. Acknowledges the "10 nodes vs. 1" complexity trade-off with honest mitigation (straight-edge corrector chain avoids conditional edge overhead).
    Code examples Concrete routing predicate functions for each gate. State write ownership table.
    Open questions Three well-formulated open questions showing design maturity.

    Strengths: - The state write ownership table ("Node → Writes") is the single best piece of documentation across all proposals. Every node writes only the fields it owns, eliminating the current plan_node's 9-way conditional out = {"decision": ..., "schema": maybe, "dynamic_decompositions": maybe} pattern. - Correctors as a straight add_edge chain (no branching, no predicates) is a genuine insight — cheaper checkpointer writes, simpler graph, yet each corrector remains independently testable. - llm_failed transient flag correctly prevents c_calc_adjust from redirecting LLM failures into calculation loops. - The "One invariant" statement ("Every gate/corrector path eventually deposits a PlannerDecision into state['decision']") is a strong architectural constraint.

    Weaknesses: - Most checkpointer writes per iteration. Even with straight-edge optimization, 10+ node hops is a measurable cost on PostgresSaver. - Splitting c_target_decompose, c_redirect_derived, c_redirect_web, c_search_cap, c_ask_cap, c_calc_adjust into individual nodes is arguably over-decomposition. GPT-5.4's argument that "one decision_policy node is enough" applies here: these correctors are always sequential, always operate on decision, and splitting them adds graph-visualization noise without improving testability beyond what splitting into a single decision_policy node would achieve. - g_region + emit_region as separate predicate/emitter pairs is elegant in theory but adds 4 nodes for 2 bootstrap questions — the graph diagram becomes tall.

    Verdict: The most intellectually thorough proposal. Its state ownership discipline, naming conventions, and invariant statement should be adopted regardless of which decomposition granularity is chosen. The corrector chain as a flat list is the right insight, but splitting every corrector into its own node is over-engineering for this codebase.

    #4: GPT-5.5 (gpt-5.5-proposal.md) ★★★★¶

    Approach: 7-node pipeline: enter_iteration → prepare_schema → require_region/require_currency → acquisition_gate → plan → normalize_decision → retry_gate → maybe_calculate

    Aspect Assessment
    Problem diagnosis Excellent context section linking to concrete project history (U+ref benchmark hops, calculator-backed component loops).
    Design clarity Best-organized proposal structure: Problem → Decision → Implementation → Tests → Consequences → Non-goals → Sources. This matches ADR format and is immediately actionable.
    Migration plan Four steps with explicit test updates. Unique: maps existing test assertions to new node targets (test_planner_decisions.py → retry_gate, maybe_calculate, etc.).
    Trade-off analysis Separate Positive and Negative consequence sections. The "Potential checkpoint compatibility concerns" note is forward-thinking.
    Code examples None (design-level only).
    Open questions None explicit, but Non-goals section functions as implicit boundary-setting.

    Strengths: - normalize_decision and retry_gate as separate, sequential nodes is a better corrector split than Opus's 6-node chain. Two nodes capture the right granularity: "fix semantic errors in the decision" vs. "enforce attempt caps on the fixed decision." - maybe_calculate as a dedicated calculator-routing node that sits after all other policy is the cleanest treatment of _adjust_calculation_decision across all proposals. - decision_origin: Literal["deterministic", "llm", "llm_error"] is a better state field than Opus's llm_failed: bool — it tracks provenance, enabling more nuanced downstream decisions. - The "Keep these responsibilities out of the outer conversation graph" section correctly prevents scope creep — this is a planner-internal refactor.

    Weaknesses: - prepare_schema handling region/currency checks via routing (not as part of the node's own logic) creates an awkward graph topology where prepare_schema conditionally routes to require_region/require_currency — but region/currency questions logically happen before schema preparation, not after. This ordering is confusing. - retry_gate after normalize_decision may create subtle ordering issues: if normalize_decision changes decision.action from search to ask_user, retry_gate should check the new action's cap, not the old one's. The proposal doesn't address this. - No code examples or routing function signatures.

    Verdict: Best-organized proposal with the strongest consequence analysis and test migration planning. The normalize_decision + retry_gate split is the right granularity for correctors. The region/currency ordering issue detracts from otherwise excellent design.

    Tier 2 — Solid, Some Gaps¶

    #5: Kimi-2.6 (kimi-2.6-proposal.md) ★★★★¶

    Approach: 8-node decomposed graph with separate ask_region/ask_currency nodes and route_direct adapter.

    Aspect Assessment
    Problem diagnosis Strong. The "god node" characterization and 9-point responsibility list are precise.
    Design clarity The decision matrix appendix (mapping every logic block to its new location with reasoning) is the proposal's standout feature — it's the best "where does this code go?" reference across all proposals.
    Migration plan Three-phase (extract helpers → register nodes → delete legacy), standard but clear.
    Trade-off analysis Benefits table (Testability / Observability / Diagram honesty / Extensibility / LLM isolation) is concise but doesn't address costs.
    Code examples None.
    Open questions None.

    Strengths: - route_direct as a tiny adapter node that bridges deterministic acquisition tasks into the same post-processing pipeline as LLM decisions is a clever, pragmatic solution to the "two sources of decisions" problem. - The guiding principle ("Each node should do ONE thing. Routing should happen at the graph level") is stated upfront and followed consistently. - Good argument for why ask_region/ask_currency should be separate nodes: "Bootstrap questions are structural, not planner-LLM decisions. The graph should show them explicitly." - Acknowledges that enforce_policy is "still the most complex node" — honest about the proposal's limits.

    Weaknesses: - enforce_policy at ~120 lines is still substantial. The proposal identifies this but doesn't offer a mitigation. - route_direct → enforce_policy and decide → enforce_policy creates two parallel paths that converge at enforce_policy, but enforce_policy must handle decisions from both sources differently (acquisition task decisions already have _adjust_calculation_decision applied in route_direct, while LLM decisions don't). This creates hidden coupling. - No discussion of state field changes or migration risks.

    Verdict: The decision matrix is the single most useful reference artifact. route_direct is a genuine innovation. Loses points for not addressing the enforce_policy complexity problem and lacking migration risk analysis.

    #6: GLM-5.1 (glm-5.1-proposal.md) ★★★½¶

    Approach: Minimal 2-node split: pre_check + acquire_or_plan

    Aspect Assessment
    Problem diagnosis Good. The 6-concern table with LLM-needed? column correctly identifies that 5/6 concerns are deterministic.
    Design clarity The PreCheckResult dataclass with Literal route tags is well-specified. The recommendation to use a separate _pre_check_route field (not pollute Action enum) is pragmatic.
    Migration plan Four phases, but Phase 3 (_build_plan_output helper extraction) is an orthogonal concern that shouldn't be a separate phase — it should happen in Phase 1.
    Trade-off analysis Risks table with 5 rows and mitigations. Reasonable.
    Code examples PreCheckResult dataclass, _build_plan_output helper signature, graph construction code.
    Open questions None explicit.

    Strengths: - Most pragmatic proposal. Acknowledges that a 2-node split may be enough as a first step toward the deeper decompositions other proposals advocate. - _build_plan_output helper to collapse 9 conditional-return patterns into a single return is the right abstraction regardless of graph topology. - The comparison table (Before vs After) with LOC counts and return path counts is concrete and honest about what changes. - Correctly identifies that acquire_or_plan is still ~200 LOC — doesn't oversell the improvement.

    Weaknesses: - acquire_or_plan at ~200 LOC still mixes LLM call, acquisition logic, and 6 post-LLM rewrite steps. This doesn't fully solve the "plan_node is too big" problem — it just moves the complexity from a 350-line function to a 200-line one. - No discussion of how the LLM call fits relative to acquisition logic — if acquire_or_plan does deterministic acquisition AND LLM planning, what determines which path is taken? - The recommendation to keep post-LLM rewriting in acquire_or_plan for Phase 1 is pragmatic but locks in complexity that GPT-5.4/DeepSeek correctly move to a separate policy node.

    Verdict: The right answer if you want the minimal change. But it doesn't go far enough — acquire_or_plan remains too large to be a single-responsibility node. Best used as Phase 1 of a more ambitious decomposition.

    #7: Qwen-3.7-Max (qwen-3.7-max-proposal.md) ★★★½¶

    Approach: 10-node pipeline: check_termination → check_region_currency → compose_schema → check_calculator → acquisition_routing → check_completion → llm_decide → post_process → enforce_caps → route_decision

    Aspect Assessment
    Problem diagnosis Thorough responsibility enumeration.
    Design clarity The graph construction code (lines 552–672) is the most complete implementation sketch — nearly copy-paste ready. Node code examples with full signatures.
    Migration plan Five phases, standard.
    Trade-off analysis Risks table, standard. Acknowledges "increased graph complexity" but mitigation is just "clear naming and documentation" — insufficient.
    Code examples Most detailed of all proposals. Every node has a full function body. This is simultaneously a strength (concreteness) and a weakness (premature implementation detail obscuring design discussion).
    Open questions None.

    Strengths: - The most "implementable" proposal — a developer could start coding from this document with minimal additional context. - check_termination as the first node with explicit _route pattern is clean. - Good handling of _llm_failed flag to prevent LLM-failure → calculator-redirect loops.

    Weaknesses: - The _route transient state pattern is used across 9 nodes. This creates a parallel routing system inside state — nodes write _route and routing functions read it. This is fragile: a node that forgets to set _route breaks silently; a node that sets the wrong _route creates routing bugs that require inspecting state dumps to debug. - route_decision as a separate node that only calls _emit_decision_event and returns decision.action is unnecessary. GPT-5.4's warning applies: this should be a routing function, not a node. - enforce_caps calls _adjust_calculation_decision inside the ask-user cap branch, but _adjust_calculation_decision also needs to be called for the normal path. The proposal handles this but the logic is scattered across the function body. - observe_user → check_region_currency edge (line 668) means user answers always re-enter through region/currency checks, but this is semantically wrong after the first iteration — region/currency are already collected.

    Verdict: The most implementation-ready proposal, but the _route pattern and unnecessary route_decision node add accidental complexity. The graph construction code is valuable as a reference implementation, but the architecture has too many nodes.

    Tier 3 — Has Useful Ideas, Significant Gaps¶

    #8: Mimo-2.5-Pro (mimo-2.5-pro-proposal.md) ★★★¶

    Approach: 3-node split: guards → acquire → decide

    Aspect Assessment
    Problem diagnosis Adequate but brief.
    Design clarity The 3-node decomposition is the simplest across all proposals — a genuine advantage for comprehension.
    Migration plan Three phases, standard.
    Trade-off analysis Benefits table (LOC counts per node) is concrete. Open questions section with 3 questions is good practice.
    Code examples guards_node and acquire_node signatures only.
    Open questions Three well-formulated questions about decide scope, plan_router as node vs. function, naming.

    Strengths: - The cleanest decomposition in terms of node count. Three nodes are easy to understand and reason about. - Good open questions (should decide include loop/cap detection or be a separate validate_decision node?) — shows awareness of the design space. - Explicit about what stays the same, reducing migration risk.

    Weaknesses: - decide at ~80 lines still mixes LLM call, deterministic acquisition-task conversion, 3 redirect functions, and cap detection. This is better than 350 lines but still violates single-responsibility. - guards mixes iteration counting, region/currency checks, AND calculator status checks. These are three distinct concerns. - No discussion of what happens when guards short-circuits to finish — does schema composition still happen? (It shouldn't, but the ordering isn't explicit.) - No routing function signatures.

    Verdict: Too minimal. The 3-node split is a step in the right direction but leaves too much complexity in decide. The open questions suggest the author knew this was incomplete.

    #9: Qwen-3.6-Plus (qwen-3.6-plus-proposal.md) ★★★¶

    Approach: Unconventional: puts post-LLM redirects into route_after_plan (edge function) rather than a node.

    Aspect Assessment
    Problem diagnosis Good. 12-point responsibility table with nature classification (Guard / Pre-flight / Preparation / etc.).
    Design clarity The "biggest win" claim — moving redirects to the routing function — is architecturally questionable (see weaknesses).
    Migration plan Five phases, each with test verification.
    Trade-off analysis Benefits table, risks table with mitigations. Standard.
    Code examples Routing function signatures with return type comments.
    Open questions Three questions about decompose as node vs. plan-internal, route_finish_check as node vs. edge, separate region/currency observe nodes.

    Strengths: - route_finish_check as a gate that validates finish decisions (checking for remaining missing fields) before allowing END is a genuinely good safety net that no other proposal includes. - Separate ask_region/ask_currency with their own observe_region/observe_currency nodes creates cleaner region/currency handling — no special-casing in the generic observe_user_node. - Good open questions about decompose placement and route_finish_check form factor.

    Weaknesses: - Critical design flaw: Putting redirect logic in route_after_plan (an edge function) violates GPT-5.4's (sound) constraint: "Conditional edges should inspect state and return route labels only. Nodes should own mutations." Post-LLM redirects (_redirect_derived_direct_decision, _redirect_premature_ask_for_web_field, _adjust_calculation_decision) mutate PlannerDecision objects — doing this in an edge function means either: 1. Mutating state in the edge (bad — checkpointer can't capture it), or 2. Returning a different route label without mutating state (then the action node gets the wrong decision).

    Neither is correct. This is the only proposal that makes this mistake. - route_finish_check as a node that conditionally routes back to plan creates a subtle loop that's hard to visualize from the graph topology alone.

    Verdict: Interesting ideas (separate region/currency observe nodes, route_finish_check safety net) but the core architectural decision (redirects in edge functions) is unsound. Adopt the individual ideas but reject the edge-function approach.

    #10: Gemini-3.1-Pro (gemini-3.1-pro-proposal.md) ★★½¶

    Approach: 3-node split: prepare_state → evaluate_rules → llm_plan

    Aspect Assessment
    Problem diagnosis Good — identifies 8 concerns and correctly calls out the "anti-pattern in LangGraph."
    Design clarity The simplest conceptual model: state prep → rules → LLM. Easy to understand.
    Migration plan Listed as 3 implementation steps, but no phasing or risk assessment.
    Trade-off analysis Benefits only (3 bullet points). No disadvantages, risks, or costs discussed.
    Code examples None.
    Open questions None.

    Strengths: - Clean conceptual separation. The "prepare → evaluate → call LLM" model is the simplest mental model across all proposals. - Good LangGraph-specific reasoning about why hidden control flow is an anti-pattern (LangSmith visibility).

    Weaknesses: - Significantly incomplete. At 117 lines, it's the shortest proposal and lacks: - Any migration strategy or phasing - Any risk assessment - Any discussion of post-LLM decision correction (the route_after_llm diagram shows no corrector nodes at all — decisions go straight from llm_plan to action nodes) - Any code examples or routing function signatures - evaluate_rules node is a catch-all for 6+ separate deterministic checks. This is the same monolithic problem — just moved from plan_node to evaluate_rules. - The claim that "nodes like observe, calculate, observe_user, and reflect should now point back to prepare_state instead of plan" means prepare_state runs on every loop-back, including when only a routing decision is needed. This couples state preparation to routing.

    Verdict: A reasonable starting outline but not a complete proposal. The 3-node split is clear but doesn't address post-LLM correction, which is a significant portion of the current plan_node logic (~120 lines). Would need substantial expansion to be actionable.

    Architecture Patterns Worth Adopting Regardless of Proposal¶

    Pattern Source Why
    State write ownership table Opus Prevents scattered schema/dynamic_decompositions writes across 9 return paths
    Single iteration-counter node GPT-5.4, GPT-5.5, Opus Prevents attempt log drift from multiple increment sites
    Canonical loop-entry node All proposals Makes checkpoint state consistent at every iteration boundary

    Straight-edge corrector chain Opus Cheaper checkpointer writes than conditional edges for sequential correctors

    Patterns to Avoid¶

    Pattern Found In Why Avoid
    _route transient state field GLM-5.1, Qwen-3.7-Max Creates a parallel routing system inside state; fragile and hard to debug
    Redirects in edge functions Qwen-3.6-Plus Edge functions are for inspection, not mutation; checkpointer can't capture changes
    Over-splitting correctors Opus (6), Qwen-3.7 (3+) Each corrector is 5-15 lines; the graph noise outweighs the testability gain
    Region/currency after schema prep GPT-5.5 Bootstrap questions should gate before expensive schema composition
    Catch-all evaluate_rules node Gemini-3.1-Pro Same monolithic problem, different name

    Recommended Architecture¶

    Primary Recommendation: DeepSeek-4-Pro + GPT-5.4 Design Principles¶

    The best solution combines DeepSeek-4-Pro's 4-node pipeline structure with GPT-5.4's design discipline:

    START → tick → guard → prepare → plan → adjust → {action nodes} → tick

    Adopt from DeepSeek-4-Pro: 1. The guard → prepare → plan → adjust pipeline topology 2. adjust as the single canonical decision-normalization node that all decision sources pass through 3. plan → plan self-loop for decomposition re-prompt 4. The 4-phase migration strategy (extract helpers → update graph → remove old code → verify) 5. recipes in state for caching (with serialization verification)

    Adopt from GPT-5.4: 1. tick as a separate iteration-lifecycle node (not merged into guard) 2. Anti-pattern constraints: no mutation in edges, only tick increments iterations, ask_user remains sole interrupt 3. Staged migration with "no rename until stable" 4. "One decision_policy node is enough" — reject the corrector-chain explosion

    Adopt from GPT-5.5: 1. decision_origin: Literal["deterministic", "llm", "llm_error"] instead of llm_failed: bool 2. Non-goals section to prevent scope creep

    Adopt from Opus: 1. State write ownership table as implementation documentation 2. g_* / c_* naming convention for self-documenting graph nodes 3. Straight-edge for sequential correctors inside adjust

    Adopt from Kimi-2.6: 1. Decision matrix format for "what-goes-where" implementation reference

    Target Graph Topology¶

    flowchart TD
    planner_start([START]) --> tick[tick]

    tick -->|aborted or max_iters| finish
    tick -->|continue| guard[guard]

    guard -->|needs region/currency| ask_user
    guard -->|ready| prepare[prepare]

    prepare -->|calc cap reached| finish
    prepare -->|calc success| finish
    prepare -->|continue| plan[plan]

    plan -->|decomposition needed| plan
    plan -->|continue| adjust[adjust]

    adjust -->|search| search[search]
    adjust -->|ask_user| ask_user[ask_user / interrupt]
    adjust -->|calculate| calculate[calculate]
    adjust -->|reflect| reflect[reflect]
    adjust -->|finish| finish[finish]

    search -->|last_observation present| observe[observe]
    search -->|no hits or backend failure| tick

    observe --> tick
    calculate --> tick
    ask_user --> observe_user[observe_user]
    observe_user --> tick
    reflect --> tick
    finish --> planner_end([END])

    Why This Combination Wins¶

    1. Graph is honest but not noisy. 5 new control nodes (tick, guard, prepare, plan, adjust) instead of 10+. Every node has a clear, single purpose visible from its name.

    2. adjust is the right abstraction. It's the single post-decision normalization stage. Both deterministic decisions (from acquisition tasks in prepare) and LLM decisions (from plan) pass through it. This eliminates the "two sources of decisions problem" that Kimi's route_direct + enforce_policy pattern creates.

    3. Migration is lowest-risk. DeepSeek-4-Pro's Phase 1 (extract helpers without graph changes) proves correctness before any topology change. GPT-5.4's staged approach ships independent, testable commits.

    4. State discipline is enforced. Opus's write-ownership model ensures nodes don't accidentally overwrite each other's fields. Only tick writes iterations. Only prepare writes schema and dynamic_decompositions. Only adjust writes the final decision.

    5. Future policy is easy to add. Adding a new bootstrap question (e.g., "ask industry before region") means adding one condition to guard and one routing path — not editing a 350-line monolith.

    Non-Goals (Per GPT-5.5)¶

    • Do not move planner logic into the outer conversation graph.
    • Do not redesign PlannerDecision action names.
    • Do not change search backend behavior.
    • Do not change schema merge or calculator semantics.
    • Do not add SQL persistence for planner internals.
    • ask_user remains the only interrupt() node.
    • Planner thread namespacing (planner_thread_id()) stays unchanged.
    • Outer run_planner_step() bootstrap/resume contract stays unchanged.

    Implementation Priority¶

    Priority Task Risk
    1 Extract helper functions from plan_node (no graph change) None
    2 Add tick node (iteration lifecycle only) Low
    3 Add guard node (region/currency bootstrap gates) Low
    4 Add prepare node (schema composition + calc lifecycle) Medium
    5 Slim plan_node to LLM-only Medium
    6 Add adjust node (post-decision normalization) Medium
    7 Rewire loop-back edges to tick Medium
    8 Remove old plan_node and update tests Low
    9 Add recipes to state + verify serialization Medium

    Conclusion¶

    The 10 proposals form a clear spectrum from minimal (GLM-5.1, 2 new nodes) to maximal (Opus, 14+ nodes). The consensus is strong: plan_node must be decomposed into graph-level nodes with deterministic policy visible in conditional edges and the LLM call isolated in a thin node.

    The best solution is not any single proposal but a synthesis:

    • DeepSeek-4-Pro provides the optimal pipeline topology (guard → prepare → plan → adjust) and the best migration strategy.
    • GPT-5.4 provides the design principles and anti-pattern constraints that prevent the refactor from creating new problems.
    • GPT-5.5 provides the best consequence analysis and decision_origin state discipline.
    • Opus provides the best state ownership model and naming conventions.
    • Kimi-2.6 provides the best "what-goes-where" reference matrix.

    The resulting architecture is a 5-node control pipeline wrapping 5 executor nodes, totalling ~10 nodes — marginally more than the current 8, but with an order-of-magnitude improvement in graph honesty, testability, and maintainability.
