    Planner graph refactor proposal ranking¶

    Scope¶

    This analysis compares the proposals in docs/planner-graph-ref/proposals against the current planner implementation in src/venturescope/planner/agent.py, the planner invocation wrapper in src/venturescope/planner/__init__.py, and the outer conversation graph in src/venturescope/conversation/graph.py.

    The common diagnosis is correct: the visible planner graph is small, but plan_node() is the real policy engine. It increments iterations, asks mandatory region/currency questions, prepares decompositions, composes schema fields, handles calculator lifecycle, selects deterministic acquisition tasks, calls the LLM, normalizes unsafe decisions, enforces retry caps, and emits planner events.

    Evaluation criteria¶

    The ranking uses these criteria:

    1. Contract safety: preserves build_planner_graph(checkpointer), run_planner_step(), planner thread ID {conversation_id}:planner, and the outer route_if_needed -> planner_step -> persist graph.
    2. Interrupt safety: keeps ask_user_node() as the single LangGraph interrupt() surface and preserves Command(resume=user_message) behavior.
    3. Checkpoint discipline: keeps planner state checkpointer-owned through State and PlannerState; avoids rich cached objects or informal transient fields unless they are formal serializer-safe state.
    4. Control-flow clarity: exposes real planner phases without turning every predicate into a checkpointed node.
    5. Behavioral completeness: preserves calculator caps/success/blocked recovery, acquisition tasks, post-LLM redirects, duplicate-search fallback, ask-user caps, and LLM-failure handling.
    6. Migration safety: allows helper extraction and test migration before graph topology changes.

    Ranked list¶

    1. gpt-5.4-proposal.md - best base architecture¶

    Verdict: Best proposal to use as the implementation spine.

    Good sides

    • Uses the right granularity: tick, bootstrap_gate, prepare_context, acquisition_gate, llm_plan, and one decision_policy node.
    • Keeps graph phases meaningful without over-atomizing every redirect or cap check.
    • Correctly keeps conditional edges side-effect free and leaves mutations in nodes.
    • Explicitly keeps ask_user as the only interrupt node.
    • Explicitly preserves the outer conversation graph and planner public surface.
    • Gives a safe migration order: extract loop entry first, then bootstrap, preparation, acquisition, LLM planning, and policy.

    Bad sides

    • Under-specifies how to carry the current llm_failed safeguard across the llm_plan -> decision_policy boundary.
    • The single decision_policy node may still be moderately complex, though that is preferable for the first implementation.
    • Needs more detail on test migration for existing plan_node() unit tests.

    2. gpt-5.5-proposal.md - best detailed target, slightly more node-heavy¶

    Verdict: Strongest detailed design; best used to refine the GPT-5.4 spine.

    Good sides

    • Cleanly separates loop entry, schema preparation, mandatory prerequisites, deterministic acquisition, LLM planning, normalization, retry policy, and calculator routing.
    • Correctly says planner logic must stay inside the planner subgraph, not conversation/graph.py.
    • Calls out the key state issue: avoid storing prepared_recipes unless serialization is proven safe.
    • Recognizes the need for llm_failed or decision_origin so calculator adjustment does not convert an LLM failure into a repeated LLM-dependent reflect loop.
    • Provides a good test migration map from plan_node() tests to new policy-node tests.

    Bad sides

    • More nodes than the GPT-5.4 proposal, so it creates more checkpointed intermediate phases.
    • require_region and require_currency as named phases are useful conceptually, but they should still route to the existing ask_user_node() rather than become new interrupt surfaces.
    • normalize_decision, retry_gate, and maybe_calculate are good long-term seams, but splitting all three immediately may be more migration risk than necessary.

    3. glm-5.1-proposal.md - safest first migration slice¶

    Verdict: Not the best final graph, but excellent as phase one.

    Good sides

    • Proposes a conservative split: pre_check plus acquire_or_plan.
    • Keeps post-LLM rewriting in acquire_or_plan for the first pass, which reduces graph churn.
    • Correctly identifies that post-LLM rewriting can become validate_decision later.
    • Focuses on a staged reduction of risk instead of a large topology rewrite.

    Bad sides

    • Leaves too much policy in acquire_or_plan for the final architecture.
    • Suggests a _pre_check_route/route-tag field; if used, that field must be formalized in both State and PlannerState or avoided by writing a real PlannerDecision and routing from it.
    • Does not expose retry and calculator normalization as clearly as the top proposals.

    4. deepseek-4-pro-proposal.md - good balanced pipeline with one state concern¶

    Verdict: Good architecture, close to the desired moderate split.

    Good sides

    • The guard -> prepare -> plan -> adjust pipeline is easy to understand.
    • Correctly routes action-node loopbacks to the new top-of-loop guard.
    • Keeps LLM planning narrow and puts deterministic correction in adjust.
    • Treats auto-complete and acquisition decisions as candidates for downstream adjustment, preserving calculator behavior.

    Bad sides

    • Proposes storing recipes: dict[str, FieldAcquisition] in state. That is risky because planner state is checkpointed and mirrored by PlannerState; FieldAcquisition serialization must not be assumed.
    • The plan -> plan self-loop for generated decompositions may add extra LLM calls and awkward checkpoints.
    • Less explicit than GPT-5.5 about LLM-failure origin and calculator adjustment safeguards.

    5. kimi-2.6-proposal.md - clear decomposition, but interrupt split is risky¶

    Verdict: Useful structure, but should not be adopted as-is.

    Good sides

    • Good node names: tick, prepare, calc_gate, acquire, decide, enforce_policy.
    • Keeps post-decision enforcement together instead of exploding it into many tiny nodes.
    • Correctly isolates the LLM call in decide.
    • Has a reasonable helper-first migration path.

    Bad sides

    • Proposes dedicated ask_region and ask_currency nodes. That creates extra interrupt surfaces or special cases; the existing ask_user_node() should remain the only interrupting node.
    • route_direct is an adapter node that may not add much value over returning a decision into a shared policy node.
    • Needs more detail on preserving run_planner_step() soft-retry and target-field behavior.

    6. opus-proposal.md - best reference for complete mapping, too atomized for first implementation¶

    Verdict: Valuable as a checklist, not as the first implementation target.

    Good sides

    • Most complete mapping from current plan_node() line ranges to future gates/correctors.
    • Correctly identifies duplicated bookkeeping around schema changes, dynamic decompositions, and LLM failure.
    • Has a disciplined staged migration: helpers first, gates second, correctors last.
    • The final dispatch idea is useful for canonical logging and event emission.

    Bad sides

    • Too many graph nodes and checkpoint boundaries for this codebase on the first pass.
    • The g_*/c_* naming scheme is internally clear but would make the graph harder for product engineers to read.
    • Splitting every corrector into a node increases replay/debug surface without enough immediate benefit.

    7. qwen-3.7-max-proposal.md - exhaustive but brittle¶

    Verdict: Strong responsibility inventory, weak implementation fit.

    Good sides

    • Covers almost every current behavior: termination, region/currency, schema composition, calculator, acquisition, completion, LLM, post-processing, caps, final routing.
    • Shows enough pseudo-code to expose hidden ordering assumptions.
    • Recognizes that LLM failure must be tracked separately from normal finish decisions.

    Bad sides

    • Heavy use of _route and _llm_failed transient fields conflicts with the current State/PlannerState serializer discipline unless formalized.
    • Says transient fields should be excluded from checkpointing, but LangGraph state updates are checkpointed by design unless the schema is deliberately structured for private channels.
    • The graph sketch references route_decision as a source node without registering a node for it.
    • Too many nodes for the first implementation.

    8. gemini-3.1-pro-proposal.md - good concept, incomplete for this planner¶

    Verdict: Useful high-level sketch, insufficient as an implementation plan.

    Good sides

    • Cleanly separates prepare_state, evaluate_rules, and llm_plan.
    • Emphasizes isolating the LLM call from deterministic rules.
    • Low cognitive overhead and easy to explain.

    Bad sides

    • Under-specifies the most dangerous current behavior: post-LLM redirects, search/ask caps, calculator adjustment, and component-derived routing.
    • Uses generic LLM language and does not account for the project’s dedicated planner LLM configuration and fake-LLM tests.
    • Needs a much stronger state/checkpoint and migration story.

    9. mimo-2.5-pro-proposal.md - too coarse and ambiguous¶

    Verdict: Has the right instinct, but the shape is not precise enough.

    Good sides

    • Identifies guards, acquire, and decide as useful seams.
    • Suggests extracting helpers before changing topology.
    • Keeps new state keys mostly unchanged.

    Bad sides

    • The acquire -> decide | finish framing is too coarse for current behavior: deterministic acquisition, auto-finish, calculator adjustment, and LLM planning are distinct concerns.
    • The plan_router node/comment is ambiguous and not fully specified.
    • Post-decision redirect and retry policy remain buried in decide, leaving too much of the current monolith intact.

    10. qwen-3.6-plus-proposal.md - most problematic as-is¶

    Verdict: Do not use as an implementation base.

    Good sides

    • Correctly sees that region/currency and decomposition are graph-visible phases.
    • Correctly wants finish validation to avoid premature termination.
    • Preserves the public run_planner_step() and build_planner_graph() surfaces.

    Bad sides

    • Moves redirect behavior into route_after_plan(). Conditional edge functions should route only; if they rewrite decisions, those mutations are invisible or unsafe for checkpointing. If they only return a different route, action nodes may receive a stale state["decision"].
    • Introduces dedicated ask_region/ask_currency and observe_region/observe_currency nodes even though observe_user_node() already owns those special cases.
    • Several loopbacks return to plan instead of the top guard/preflight path, which risks skipping iteration and prerequisite checks after action nodes.
    • Duplicates finish semantics despite finish_node() already checking missing/open acquisition work.

    Recommended solution¶

    Use a combination rather than adopting one proposal verbatim:

    1. Use gpt-5.4-proposal.md as the base graph shape: tick -> bootstrap_gate -> prepare_context -> acquisition_gate -> llm_plan -> decision_policy -> action nodes.
    2. Borrow from gpt-5.5-proposal.md:
    3. explicit llm_failed or decision_origin handling;
    4. no cached FieldAcquisition recipes in checkpoint state unless proven safe;
    5. keep planner policy inside the planner subgraph;
    6. migrate tests from plan_node() to phase-specific nodes.
    7. Borrow from glm-5.1-proposal.md for the first implementation slice: extract helpers and optionally create a conservative pre_check phase before changing the whole graph.
    8. Keep Opus as a later checklist if decision_policy remains too large, but do not split every corrector into nodes in the first pass.

    Suggested target graph¶

    flowchart TD
    planner_start([START]) --> tick[tick]
    tick -->|aborted or max_iters| finish[finish]
    tick -->|continue| bootstrap_gate[bootstrap_gate]

    bootstrap_gate -->|needs region/currency| ask_user[ask_user / interrupt]
    bootstrap_gate -->|ready| prepare_context[prepare_context]

    prepare_context --> acquisition_gate[acquisition_gate]
    acquisition_gate -->|deterministic decision| decision_policy[decision_policy]
    acquisition_gate -->|needs LLM| llm_plan[llm_plan]

    llm_plan --> decision_policy
    decision_policy -->|search| search[search]
    decision_policy -->|ask_user| ask_user
    decision_policy -->|reflect| reflect[reflect]
    decision_policy -->|calculate| calculate[calculate]
    decision_policy -->|finish| finish

    search -->|last_observation present| observe[observe]
    search -->|no observation| tick
    observe --> tick
    calculate --> tick
    reflect --> tick
    ask_user --> observe_user[observe_user]
    observe_user --> tick
    finish --> planner_end([END])

    This graph is intentionally less detailed than GPT-5.5 and Opus. It exposes the real lifecycle while limiting checkpoint churn.

    Implementation guidance¶

    1. Extract helpers without graph changes first. Preserve plan_node() behavior while creating helper seams that mirror future nodes.
    2. Move only loop-entry behavior first. tick should be the only place that increments iterations and emits the planning-step event.
    3. Keep ask_user_node() as the interrupt surface. Bootstrap gates should create PlannerDecision(action="ask_user", ...) and route to the existing node.
    4. Keep edge functions pure. They should inspect state and return route labels only; all state mutation belongs in nodes.
    5. Add only serializer-safe state. If decision_origin is needed, add it deliberately to both State and PlannerState, clear it at loop entry, and test restart safety.
    6. Do not store rich recipes in state initially. Rebuild recipes from dynamic_decompositions and static_field_acquisition unless profiling proves this is too expensive.
    7. Preserve the action nodes. search_node, observe_node, calculate_node, ask_user_node, observe_user_node, reflect_node, and finish_node should remain behaviorally unchanged in the first graph refactor.
    8. Move tests by behavior, not by old function name. Existing plan_node() tests should become tests for bootstrap_gate, acquisition_gate, llm_plan, and decision_policy; integration tests around run_planner_step() and restart safety should stay.

    Final advice¶

    Adopt the moderate phased graph split: GPT-5.4 as the graph spine, GPT-5.5 for state/test/LLM-failure details, and GLM for the low-risk migration path.

    Do not adopt the fully atomized Opus/Qwen shape as the first implementation. It is accurate as an analysis artifact, but it creates too many checkpointed boundaries before the team has proven equivalence. Do not adopt proposals that mutate routing functions, add extra interrupt nodes, or add informal transient state. Those choices are the most likely to break LangGraph resume semantics and planner checkpoint compatibility.
