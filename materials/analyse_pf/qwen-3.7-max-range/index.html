    Planner Graph Refactor: Proposal Evaluation¶

    Author: Sisyphus (qwen-3.7-max) Date: 2026-06-08 Scope: Evaluation of 10 proposals in docs/planner-graph-ref/proposals/

    Evaluation Criteria¶

    Each proposal is assessed on seven dimensions weighted by project impact:

    Criterion Weight What it measures
    Architectural soundness High Does the graph topology correctly capture the planner lifecycle without lying about control flow?
    Right-sized decomposition High Enough nodes to separate concerns, not so many that the graph becomes noise. Sweet spot: 4-7 new nodes.
    Migration safety High Staged path where each step ships green tests. No big-bang rewrites.
    State management Medium Minimal new state fields. No mutation in edge functions. Clean checkpoint behavior.
    LangGraph alignment Medium Follows LangGraph conventions: nodes own mutations, edges are pure predicates, interrupts stay at surface nodes.
    Testability improvement Medium Each extracted node can be unit-tested without scripting the full planner LLM.
    Completeness Medium Covers all 12 responsibilities currently in plan_node, including edge cases like LLM failure and calculator-blocked loops.

    Ranked Proposals¶

    #1: gpt-5.4-proposal — 6-node pipeline with staged migration¶

    Nodes: tick → bootstrap_gate → prepare_context → acquisition_gate → llm_plan → decision_policy

    Strengths:

    • Best "do not" section of any proposal. Explicitly warns against state mutation in edge functions, iteration increment in gates, and turning every policy rule into a node. This alone prevents the three most common LangGraph refactoring mistakes.
    • 6-stage migration where each stage ships independently. Stage 1 (extract tick) is a 20-line change that immediately improves the graph. Each subsequent stage is a focused, reviewable PR.
    • decision_policy as a single post-LLM node is the right call. Splitting every redirect into its own node (as opus proposes) adds graph noise without improving clarity. The redirect functions are pure transformations on PlannerDecision — they belong together.
    • "What should not change" section explicitly preserves ask_user as the only interrupt node, planner thread namespacing, and the outer run_planner_step() contract. This prevents scope creep.
    • Naming is honest. tick, bootstrap_gate, acquisition_gate describe what the nodes actually do. No abstract names like pre_check or guards.

    Weaknesses:

    • bootstrap_gate as a separate node for just region/currency checks is thin (~20 lines). Could be merged into tick or prepare_context without losing clarity.
    • No code examples — less concrete than proposals that include function signatures.
    • Doesn't explicitly address the _build_plan_output problem (9 conditional-return paths assembling state dicts).

    Verdict: Best overall balance of decomposition granularity, migration safety, and practical guidance. The anti-pattern warnings are worth adopting regardless of which proposal is chosen.

    #2: deepseek-4-pro-proposal — 4-node pipeline (guard → prepare → plan → adjust)¶

    Nodes: guard → prepare → plan → adjust

    Strengths:

    • Most pragmatic node count. 4 new nodes is the minimum viable decomposition that actually solves the monolith problem. Each node has a clear, non-trivial purpose.
    • recipes in state avoids redundant build_dynamic_recipes() calls across nodes. Currently this dict is recomputed in plan_node, observe_user_node, and elsewhere. Caching it in state is a genuine improvement, not just restructuring.
    • plan self-loop for decomposition is an elegant solution to the "LLM targets a composite field that hasn't been decomposed yet" problem. The conditional edge loops back to plan with updated recipes, avoiding a separate corrector node.
    • Detailed alternatives section explicitly considers and rejects deeper decomposition (16 nodes), edge-only overrides, calculator subgraph, and minimal guard-only extraction. Shows the author thought about the design space.
    • Phase 1 extraction before Phase 2 graph changes is the safest migration order. Helpers are extracted and tested before any topology changes.

    Weaknesses:

    • recipes in state needs serialization care. FieldAcquisition objects must be checkpoint-safe. The proposal mentions this but doesn't detail the serialization format.
    • guard at ~20 lines is thin. It handles only iteration counting and region/currency checks. Could absorb more from prepare (e.g., calculator caps).
    • The plan self-loop adds a subtle conditional edge that's easy to get wrong during implementation.

    Verdict: Best choice if the team prefers minimal graph changes. The 4-node pipeline is the smallest decomposition that still makes the Mermaid diagram truthful. Slightly less granular than gpt-5.4 but more pragmatic.

    #3: gpt-5.5-proposal — 8-node control pipeline¶

    Nodes: enter_iteration → prepare_schema → require_region/require_currency → acquisition_gate → plan → normalize_decision → retry_gate → maybe_calculate

    Strengths:

    • Most thorough analysis. The node responsibility split section reads like a specification. Every responsibility from plan_node is explicitly assigned to a node with a clear contract.
    • llm_failed / decision_origin state addition is well-reasoned. The current code has a subtle bug where a failed LLM call can trigger a reflect redirect that fails again. Tracking decision origin prevents this.
    • Best "Consequences" section with honest negatives: more nodes, more state handoff discipline, migration risk, checkpoint compatibility concerns. Most proposals only list positives.
    • Explicit non-goals prevent scope creep: no outer graph changes, no PlannerDecision redesign, no search backend changes, no schema merge changes.
    • Test migration guidance tells you which existing tests move to which new nodes.

    Weaknesses:

    • 8 nodes is over-decomposed. require_region and require_currency as separate nodes for ~15 lines each is excessive. They should be branches within a single bootstrap_gate or merged into prepare_schema.
    • 3 post-LLM nodes (normalize_decision → retry_gate → maybe_calculate) adds 3 checkpoint writes per iteration for logic that's pure PlannerDecision transformation. gpt-5.4's single decision_policy node handles the same logic with one hop.
    • More state handoff discipline needed (acknowledged in negatives). With 8 nodes, each writing different state fields, the risk of accidental cross-writes is real.

    Verdict: Best documentation and analysis, but the graph is over-decomposed. Take the analysis and apply it to a 5-6 node topology (merge require_region/require_currency, merge the 3 post-LLM nodes).

    #4: glm-5.1-proposal — 2-node conservative split (pre_check → acquire_or_plan)¶

    Nodes: pre_check → acquire_or_plan

    Strengths:

    • Most conservative approach. Only 2 new nodes, minimal graph topology change. Lowest migration risk of any proposal.
    • Option A/B for post-LLM rewriting is smart engineering judgment. Option A (keep in acquire_or_plan for first pass) is the right call. Extracting to validate_decision later if needed avoids premature decomposition.
    • _build_plan_output helper is a unique contribution no other proposal mentions. The current 9-way conditional-return pattern in plan_node (assembling out = {"decision": ..., "iterations": ..., "status": ...} with conditional schema and dynamic_decompositions merges) is a real readability problem. This helper collapses it.
    • _pre_check_route field for clean routing without polluting PlannerDecision.action with guard-only variants.
    • Thorough risk table with specific mitigations per risk.

    Weaknesses:

    • acquire_or_plan at ~200 LOC is still a monolith. The proposal acknowledges this but defers the fix to an optional Phase 4. The core problem — LLM call mixed with acquisition logic and post-LLM rewriting — remains largely unsolved.
    • Only 2 nodes doesn't make the Mermaid diagram much more truthful. The graph still shows acquire_or_plan → action without revealing the calculator gates, auto-finish checks, or redirect logic inside.
    • Phase 4 (extract validate_decision) is marked optional but it's the most important extraction for testability. Without it, testing post-LLM redirects still requires scripting the full LLM call.

    Verdict: Best choice if the team wants minimal risk and is willing to accept an incomplete solution. The _build_plan_output helper should be adopted regardless — it's a standalone improvement.

    #5: kimi-2.6-proposal — 8-node pipeline with decision matrix¶

    Nodes: tick → ask_region/ask_currency → prepare → calc_gate → acquire → route_direct → decide → enforce_policy

    Strengths:

    • Decision matrix appendix (what goes where table) is the clearest mapping from old code to new nodes of any proposal. Every logic block has a specific destination with a reason.
    • enforce_policy as single post-LLM node is correct. All redirects, cap enforcement, and calculator adjustments in one place.
    • route_direct as adapter node is a nice touch — it bridges deterministic acquisition tasks into the same post-processing pipeline as LLM decisions, ensuring _adjust_calculation_decision always runs.
    • Legacy wrapper option for phased migration: plan_node becomes a thin orchestrator that chains the new nodes internally before the graph topology changes.

    Weaknesses:

    • ask_region and ask_currency as separate nodes is overkill. These are 15-line decision constructors that differ only in target_field and user_question. A single bootstrap_gate with conditional edges handles both.
    • route_direct as a separate node for acquisition task → PlannerDecision conversion adds a graph hop for what's essentially a 5-line adapter function. This could be inline in acquire.
    • calc_gate for 2 predicates (cap reached, success) is thin. These are simple boolean checks that don't justify a dedicated node.
    • 8 nodes total with several thin ones creates unnecessary graph complexity.

    Verdict: Good analysis undermined by over-decomposition of thin concerns. The decision matrix is worth adopting; the node count should be reduced to 5-6.

    #6: opus-proposal — 16+ node gate/corrector pipeline¶

    Nodes: g_iter_cap → g_region → emit_region → g_currency → emit_currency → enrich_schema → g_calc_caps → emit_calc_abort → emit_calc_done → acquire → plan_llm → c_target_decompose → c_redirect_derived → c_redirect_web → c_search_cap → c_ask_cap → c_calc_adjust → dispatch

    Strengths:

    • Most detailed node-by-node mapping from old code lines to new nodes. The table in section 4 is a line-by-line accounting of the entire 350-line function.
    • Gate/corrector naming convention (g_* for gates, c_* for correctors) is elegant and makes the graph self-documenting.
    • State ownership table (which node writes which fields) eliminates the duplicated schema_changed / dynamic_decomps bookkeeping that plagues the current code.
    • 3-step migration with risk assessment per step. Step 1 (helper extraction) is risk-free and immediately useful.

    Weaknesses:

    • 16+ nodes is far too many. The Mermaid diagram in section 3 is harder to follow than the current plan_node code. The graph becomes a spaghetti of tiny nodes connected by conditional edges.
    • Corrector chain (6 sequential nodes) adds 6 PostgresSaver checkpoint writes per iteration. The proposal acknowledges this ("Likely measurable but small") but underestimates the operational cost. Each hop is a database round-trip under PostgresSaver.
    • emit_region / emit_currency as separate nodes from their predicates (g_region / g_currency) is over-engineering. A predicate + emit in one node is standard LangGraph practice.
    • Open question #1 (should enrich_schema always run?) reveals the design isn't settled. If enrichment is wasteful for soon-to-be-aborted plans, the gate ordering needs rethinking.
    • The diagram lies in a different way. It shows 16+ nodes but doesn't show that the c_* corrector chain is a straight line with no branching. The visual complexity doesn't match the actual complexity.

    Verdict: Best code-level analysis, worst graph design. The gate/corrector pattern is elegant in theory but impractical at this scale. Take the line-by-line mapping and state ownership table; apply them to a 5-6 node topology.

    #7: qwen-3.6-plus-proposal — 6+ nodes with redirect-in-edge approach¶

    Nodes: preflight → ask_region/ask_currency → observe_region/observe_currency → decompose → plan → route_finish_check

    Strengths:

    • route_finish_check for auto-finish validation is a unique insight no other proposal includes. Currently, plan → finish is a blind pass-through. Validating that finish is actually appropriate (cap checks, missing field scan) before allowing END catches a real class of bugs.
    • Detailed code-level analysis with line numbers makes it easy to verify the proposal against the actual code.
    • 5-phase migration is well-sequenced.

    Weaknesses:

    • Redirects in route_after_plan (an edge function) means state mutation in edges. The proposal moves _redirect_derived_direct_decision, _redirect_premature_ask_for_web_field, and _adjust_calculation_decision into the routing function. These functions mutate decision — they are not pure predicates. This violates LangGraph best practices and the project's own conventions (gpt-5.4 explicitly warns: "Do not move state mutation into edge functions").
    • observe_region / observe_currency as separate nodes duplicates observe_user logic. Currently _handle_region_answer / _handle_currency_answer are called from observe_user_node via target field check. Separating them creates 3 observe nodes where 1 suffices.
    • ask_region / ask_currency as separate interrupt nodes when ask_user already handles interrupts. The interrupt payload is the same shape regardless of target field.

    Verdict: Good analysis undermined by the redirect-in-edge anti-pattern. The route_finish_check insight should be adopted by other proposals, but the edge mutation approach must be rejected.

    #8: qwen-3.7-max-proposal — 10-node full decomposition¶

    Nodes: check_termination → check_region_currency → compose_schema → check_calculator → acquisition_routing → check_completion → llm_decide → post_process → enforce_caps → route_decision

    Strengths:

    • Most complete code examples. Full function implementations for every node, including edge cases like ValueError handling in compose_schema_node and the LLM failure fallback in llm_decide_node.
    • Covers every single code path from the original plan_node. No responsibility is left unassigned.
    • _route transient field pattern is clean for routing without polluting PlannerDecision.

    Weaknesses:

    • 10 nodes is over-decomposed. check_termination (10 lines) and check_region_currency (15 lines) could be one guard node. check_calculator (15 lines) could be part of acquisition_routing.
    • route_decision as a separate "node" that just reads decision.action and emits an event is unnecessary. This is a routing function, not a node. The proposal confuses the two.
    • _route field in state needs checkpoint exclusion ("These fields should be excluded from checkpointing and cleared after use"). This adds serialization complexity that no other proposal requires.
    • check_completion duplicates acquisition logic. It calls next_acquisition_task() with the same parameters as acquisition_routing. The two nodes should be merged.
    • Code examples are so detailed they might be wrong in subtle ways. For example, route_decision is listed as both a node (builder.add_node("route_decision", ...)) and a routing function (builder.add_conditional_edges("route_decision", route_decision, ...)). The naming collision is confusing.

    Verdict: Most thorough implementation detail, but over-engineered. The code examples are useful as reference implementations for whichever proposal is chosen, but the 10-node topology should be reduced to 5-6 nodes.

    #9: gemini-3.1-pro-proposal — 3-node minimal split¶

    Nodes: prepare_state → evaluate_rules → llm_plan

    Strengths:

    • Simplest decomposition. 3 nodes is easy to understand and migrate.
    • Clear separation of concerns: state mutation, deterministic rules, LLM heuristic.

    Weaknesses:

    • evaluate_rules is still a monolith. It handles max_iters, aborted, region, currency, calculator caps, calculator success, blocked calculator, acquisition tasks, and auto-finish — approximately 150 lines of interleaved checks. The core problem (mixed concerns in one function) is not solved, just renamed.
    • No post-LLM rewriting handling. The proposal doesn't mention where _redirect_derived_direct_decision, _redirect_premature_ask_for_web_field, _adjust_calculation_decision, or cap enforcement live. These are ~120 lines of the current plan_node that simply disappear from the analysis.
    • No migration plan beyond "extract three functions and rebuild the graph." No phased approach, no risk assessment, no test strategy.
    • Shortest proposal (117 lines) with the least detailed analysis. Several responsibilities from plan_node are not addressed at all.

    Verdict: Insufficient analysis. The 3-node split doesn't solve the monolith problem — it just moves most of it into evaluate_rules. The missing post-LLM rewriting handling is a critical gap.

    #10: mimo-2.5-pro-proposal — 3-node minimal split (guards → acquire → decide)¶

    Nodes: guards → acquire → decide

    Strengths:

    • Clean migration path with 3 phases and explicit risk levels per phase.
    • Open questions section shows awareness of trade-offs (should decide include cap detection? should plan_router be a node or function?).

    Weaknesses:

    • decide at ~80 lines still includes all post-LLM redirectors AND cap enforcement. The proposal lists these as decide responsibilities: "Apply decision redirectors" (3 functions) and "Apply loop/cap detection" (2 checks). That's ~100 lines of policy logic in the "LLM caller" node. The monolith is not decomposed — it's relabeled.
    • plan_router reference in graph construction is confusing. The code shows builder.add_edge("decide", "plan_router") but plan_router is never defined as a node. It's unclear whether this is a routing function or a node.
    • Missing: how does route_after_plan work now? The proposal shows route_after_plan reading decision.action but doesn't explain where the redirects happen if decide already applied them.
    • Least detailed proposal (244 lines) with the least code-level analysis. No line-number mapping, no state ownership, no risk table.

    Verdict: Insufficient decomposition. The decide node carries too much responsibility. The proposal identifies the right concerns but doesn't actually separate them.

    Recommendation¶

    Primary: Adopt gpt-5.4's topology with deepseek-4-pro's pragmatism¶

    The best solution is a hybrid that takes:

    1. gpt-5.4's 6-node pipeline as the target topology, with one adjustment: merge bootstrap_gate into prepare_context (region/currency checks are preparation, not a separate phase). This gives a 5-node pipeline:
    tick → prepare_context → acquisition_gate → llm_plan → decision_policy

    1. deepseek-4-pro's recipes in state to avoid redundant build_dynamic_recipes() calls. This is a genuine performance improvement, not just restructuring.

    2. deepseek-4-pro's Phase 1 extraction (helpers before graph changes) as the migration starting point. This is the safest first step.

    3. gpt-5.4's anti-pattern warnings as implementation guardrails. Print them and tape them to the monitor.

    4. glm-5.1's _build_plan_output helper to collapse the 9-way conditional-return pattern. This is a standalone improvement that can ship before any graph changes.

    5. qwen-3.6-plus's route_finish_check as a validation step between decision_policy and finish. This catches a real class of bugs where the planner finishes prematurely.

    6. gpt-5.5's llm_failed state field to prevent the failed-LLM → reflect → fail-again loop.

    Resulting target graph:¶

    flowchart TD
    START --> tick
    tick -->|aborted or max_iters| finish
    tick -->|continue| prepare_context

    prepare_context -->|needs region/currency| ask_user
    prepare_context -->|ready| acquisition_gate

    acquisition_gate -->|deterministic decision| decision_policy
    acquisition_gate -->|needs LLM| llm_plan

    llm_plan --> decision_policy

    decision_policy -->|search| search
    decision_policy -->|ask_user| ask_user
    decision_policy -->|reflect| reflect
    decision_policy -->|calculate| calculate
    decision_policy -->|finish| finish_check

    finish_check -->|actually done| finish
    finish_check -->|not done| tick

    search -->|observation| observe
    search -->|no hits| tick
    observe --> tick
    calculate --> tick
    ask_user --> observe_user
    observe_user --> tick
    reflect --> tick
    finish --> END

    6 new nodes (tick, prepare_context, acquisition_gate, llm_plan, decision_policy, finish_check). Right-sized. Truthful Mermaid diagram. Each node testable in isolation.

    Migration order:¶

    1. Extract _build_plan_output helper (standalone improvement, no graph change)
    2. Extract tick (iteration + terminal checks)
    3. Extract prepare_context (bootstrap + decomposition + composition)
    4. Extract acquisition_gate (calculator + acquisition + auto-finish)
    5. Slim plan_node to llm_plan (LLM call only)
    6. Extract decision_policy (all post-LLM rewrites)
    7. Add finish_check (auto-finish validation)
    8. Add recipes and llm_failed to state

    Each step ships green tests. No big-bang rewrite.
