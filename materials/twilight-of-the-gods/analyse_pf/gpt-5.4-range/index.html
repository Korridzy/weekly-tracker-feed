    Planner graph refactor proposal ranking¶

    Scope and evaluation lens¶

    I ranked the proposals against the current planner implementation in src/venturescope/planner/agent.py, the planner runtime contract in src/venturescope/planner/__init__.py, and the checkpoint/state constraints in src/venturescope/planner/schema.py plus src/venturescope/checkpoint_serde.py.

    The most important criteria were:

    1. Semantic fidelity to the current plan_node() ordering and behavior.
    2. Checkpoint safety for State / PlannerState and nested planner thread resume.
    3. LangGraph fit: nodes mutate, edges route, interrupts stay explicit.
    4. Migration risk: can this land without breaking run_planner_step() and existing tests.
    5. Graph signal-to-noise: enough phases to make the graph honest, not so many that it becomes a checkpoint lattice.

    Current constraints that the best proposal must respect¶

    • Planner state is checkpoint-owned and mirrored by PlannerState; new state fields are compatibility work, not free.
    • run_planner_step() derives per-turn search history from iterations, so only one loop-entry phase should increment that counter.
    • ask_user is the current single interrupt() node; observe_user_node() already handles region/currency answers.
    • The outer conversation graph should stay route_if_needed -> planner_step -> persist.
    • tests/planner/test_planner_decisions.py imports plan_node() directly today, so renaming that symbol should happen late.

    Ranked list¶

    1. docs/planner-graph-ref/proposals/gpt-5.4-proposal.md¶

    Why it ranks first: best balance between architectural clarity and implementation safety.

    Good - Splits the graph at durable phases: tick -> bootstrap_gate -> prepare_context -> acquisition_gate -> llm_plan -> decision_policy. - Explicitly protects the two highest-risk invariants: only tick increments iterations, and edge functions stay side-effect free. - Keeps ask_user as the only interrupting node and keeps the outer conversation graph unchanged. - Uses one post-LLM decision_policy node instead of exploding every rewrite into a separate checkpoint boundary.

    Bad - If llm_plan and decision_policy become separate nodes, LLM-failure provenance still needs one careful handoff so finish is not rewritten into a failing reflect loop. - The migration order is good, but helper extraction is less explicit than the strongest parts of gpt-5.5 / glm-5.1.

    2. docs/planner-graph-ref/proposals/gpt-5.5-proposal.md¶

    Why it ranks second: the strongest migration discipline, with a slightly more granular final graph than I would choose for the first refactor.

    Good - Excellent staged plan: extract helpers first, add node groups gradually, delay renaming plan_node() until behavior is stable. - Very strong on repo-fit constraints: keep the planner inside the planner subgraph, keep the outer graph unchanged, keep state additions minimal. - Correctly warns against caching prepared_recipes in planner state unless serialization is proven safe. - Separates deterministic acquisition, decision normalization, retry policy, and calculator policy in a way that is easy to test.

    Bad - normalize_decision -> retry_gate -> maybe_calculate is probably one split too far for the first landing. - Likely needs an explicit llm_failed/origin bit if calculator routing is truly moved into a later node.

    3. docs/planner-graph-ref/proposals/glm-5.1-proposal.md¶

    Why it ranks third: safest incremental posture, but weaker as the final target architecture.

    Good - pre_check -> acquire_or_plan is an easy first structural win and would already make the graph more truthful. - Strong recommendation to keep post-LLM rewrites inline on the first pass, which lowers migration risk. - Good call to re-route all loopbacks through the loop-entry phase rather than back into the middle of planning. - The _build_plan_output(...) helper idea is useful regardless of final graph shape.

    Bad - Leaves too much policy inside acquire_or_plan; the monolith gets smaller, but not truly resolved. - Relies on a _pre_check_route / route-tag style field, which adds checkpoint-surface complexity that the top two proposals mostly avoid.

    4. docs/planner-graph-ref/proposals/deepseek-4-pro-proposal.md¶

    Why it ranks fourth: strong phase model, but it introduces state and control-flow ideas I would not adopt.

    Good - guard -> prepare -> plan -> adjust is a clean mental model and maps well to the real planner lifecycle. - Correctly keeps calculator and acquisition policy out of the LLM node. - Keeps the LLM node relatively small and pushes deterministic rewrites into a dedicated adjustment phase.

    Bad - Adds recipes to planner state; that increases checkpoint payload and serializer/compatibility risk for little gain. - The self-loop to re-prompt after generating a decomposition changes behavior more than necessary; the current planner does not need an extra LLM cycle for every late decomposition.

    5. docs/planner-graph-ref/proposals/kimi-2.6-proposal.md¶

    Why it ranks fifth: good decomposition instincts, but slightly too pipeline-heavy and more explicit than the runtime needs.

    Good - Clear distinction between deterministic acquisition and true LLM planning. - enforce_policy as one place for redirects and retry caps is directionally right. - Strong emphasis on graph honesty and one-node-one-job discipline.

    Bad - Dedicated ask_region / ask_currency nodes duplicate behavior that can stay as deterministic decisions routed into the existing ask_user node. - The graph is chattier than necessary, especially for bootstrap-specific branches that the current runtime already handles cleanly through ask_user -> observe_user.

    6. docs/planner-graph-ref/proposals/opus-proposal.md¶

    Why it ranks sixth: some of the best decomposition analysis, but the proposed graph is over-modeled for this codebase.

    Good - Excellent concern mapping; it sees the hidden state machine inside plan_node() very clearly. - The three-step migration strategy is disciplined and realistic. - The warning about node-hop/checkpoint overhead is accurate.

    Bad - The g_*, emit_*, c_*, dispatch lattice creates too many checkpoint boundaries for a planner that already has clear durable phases. - It overfits the graph to every internal rule, which makes the final topology harder to operate than the current monolith. - The proposal text is also a little branch-stale in places, including wrong path references (venturescope_sec) and outdated test filenames.

    7. docs/planner-graph-ref/proposals/gemini-3.1-pro-proposal.md¶

    Why it ranks seventh: good high-level instinct, not enough implementation detail to trust as a direct blueprint.

    Good - The prepare_state -> evaluate_rules -> llm_plan framing is easy to understand and explain. - Correctly identifies the hidden deterministic waterfall before the LLM call. - Keeps the LLM isolated.

    Bad - Too vague about post-LLM rewrites, retry caps, and calculator adjustment, which are some of the highest-risk parts of the current planner. - The final graph shape is too coarse to be a safe implementation plan on its own.

    8. docs/planner-graph-ref/proposals/qwen-3.6-plus-proposal.md¶

    Why it ranks eighth: it improves visibility, but it crosses a LangGraph line I would avoid.

    Good - Sees the same durable phases as the better proposals: preflight, preparation, planning, finish validation. - Tries to make redirect behavior explicit rather than leaving it buried in plan_node().

    Bad - Moves redirect and cap logic into route_after_plan(), which makes edge functions policy executors instead of pure routers. - Adds extra bootstrap-specific observe nodes even though the existing observe_user_node() already owns that resume handling. - route_finish_check feels like a back-loaded revalidation node instead of a clean deterministic gate before planning.

    9. docs/planner-graph-ref/proposals/mimo-2.5-pro-proposal.md¶

    Why it ranks ninth: the migration framing is sensible, but the actual topology is under-specified and partly inconsistent.

    Good - A three-node guards -> acquire -> decide split is easy to migrate toward. - The phase-1 recommendation to keep plan_node as an orchestrator is practical.

    Bad - The proposed flow does not cleanly represent the real branches between deterministic acquisition, completion, and “LLM still needed”. - decide still carries too much logic, so the graph becomes only marginally more truthful. - plan_router / inline-routing treatment is not fully resolved.

    10. docs/planner-graph-ref/proposals/qwen-3.7-max-proposal.md¶

    Why it ranks tenth: most ambitious, but least compatible with the current checkpoint contract.

    Good - Very explicit about guard, composition, acquisition, completion, and post-process stages. - Makes debugging paths visible.

    Bad - Adds _route and _llm_failed as transient state and then says they should be excluded from checkpointing; that clashes with the current State / PlannerState / serializer model. - Over-splits the planner into a long routing chain with many checkpoint boundaries. - Some of the mechanics are shaky as written, including a route_decision stage that is described more like a router function than a durable node contract.

    Recommendation¶

    Best target architecture¶

    Use the gpt-5.4 target graph as the end-state architecture:

    tick -> bootstrap_gate -> prepare_context -> acquisition_gate -> llm_plan -> decision_policy -> action

    with all action loopbacks returning to tick.

    That is the best fit for this repo because it:

    • makes the graph honest without turning it into a policy lattice,
    • preserves the planner’s checkpoint-owned state model,
    • keeps interrupts concentrated in ask_user,
    • keeps iteration semantics compatible with run_planner_step(), and
    • gives good test seams around the phases that actually matter.

    Best implementation strategy¶

    Use gpt-5.5 plus glm-5.1 as the migration playbook, not as the final graph shape.

    In practice:

    1. Extract pure helpers inside the current plan_node() first.
    2. Introduce tick and route all loopbacks through it.
    3. Extract bootstrap_gate and prepare_context.
    4. Extract acquisition_gate.
    5. Slim plan_node() down to the LLM-only role.
    6. Extract one decision_policy node last.
    7. Keep the exported plan_node() symbol until tests and docs are updated.

    Ideas worth borrowing from lower-ranked proposals¶

    • From DeepSeek: the simple guard/prepare/plan/adjust mental model.
    • From GLM: _build_plan_output(...) style consolidation of repeated state-assembly code.
    • From Kimi: the clear split between deterministic acquisition and LLM proposal.
    • From Opus: the insistence on stage-by-stage migration, but not its micro-node lattice.

    Explicitly reject these ideas¶

    • Mutating edge functions (qwen-3.6 style).
    • Persistent route tags or transient checkpoint-exclusion tricks (qwen-3.7 style).
    • Caching recipes or acquisition objects in planner state unless serializer and compatibility needs are proven.
    • Separate bootstrap interrupt nodes unless the existing ask_user -> observe_user path becomes insufficient.
    • Splitting every corrector into its own node on the first refactor.

    Bottom line¶

    If the goal is the best actual planner refactor, not the most elaborate Mermaid diagram, the answer is:

    Adopt the gpt-5.4 architecture, execute it with gpt-5.5 / glm-5.1 migration discipline, and borrow only selective ideas from the more aggressive proposals.
