    Planner Graph Refactor — Proposal Ranking and Analysis¶

    Reviewer: Sisyphus (Claude Opus 4.7) Date: 2026-06-08 Source proposals: docs/planner-graph-ref/proposals/*.md (10 proposals) Reference: docs/planner-graph-ref/current-graph.md

    1. Evaluation framework¶

    All ten proposals agree on the same problem statement: plan_node() (≈350 lines) is a god-node that hides 7–12 distinct concerns behind a trivial route_after_plan that just returns decision.action. They diverge on how aggressively to split that monolith and where to draw the boundaries.

    I rank each proposal against the following axes:

    Axis What I am asking
    Graph honesty Does the resulting Mermaid diagram describe the real control flow?
    Granularity fit Are nodes scoped at a useful unit of work — neither monolithic nor chatty?
    LangGraph idiom Do nodes own mutations, edges stay pure, single-interrupt invariant preserved?
    Migration risk Can the change ship in incremental steps without breaking checkpoints/tests?
    State surface How clean are the additions to State / PlannerState?
    Test seams Do the new node boundaries give us unit-testable surfaces for retry caps, calculator routing, redirects, etc.?
    Document quality Is the proposal precise (line ranges, helper names, edge maps) or just sketched?

    A strong proposal scores well on graph honesty + idiom + migration, not just on "smallest diff" or "most nodes".

    2. Ranked proposals (best → weakest)¶

    #1 — gpt-5.4-proposal.md (recommended baseline)¶

    Six-node pipeline: tick → bootstrap_gate → prepare_context → acquisition_gate → llm_plan → decision_policy → <action>.

    What is good:

    • Best balance of granularity. Six phases is enough to expose the real lifecycle (iteration, bootstrap, prep, deterministic acquire, LLM, normalization) without descending into per-rule fragmentation.
    • Explicit anti-patterns section ("do not move mutations into edges", "do not turn every rule into a node", "do not increment iterations in every gate", "do not move interrupts into policy gates"). This is exactly the discipline that several other proposals lack.
    • Single decision_policy node consolidates the five post-LLM rewrites instead of chaining them. This is the correct trade-off: the rewrites are sequential, pure transformations on a single PlannerDecision — separate nodes for each would add checkpoint hops without improving clarity.
    • Migration order is staged correctly: extract tick first (cheapest, lowest blast radius), then bootstrap_gate, then prepare_context, then acquisition_gate, then slim llm_plan_node, finally decision_policy. Each stage ships green.
    • Explicit non-goals: keeps ask_user as the only interrupt, keeps run_planner_step() contract, keeps domain helpers owning business logic.
    • Edge purity discipline is called out directly: "conditional edge functions should stay simple and side-effect free."

    What is weak:

    • No explicit handling of the LLM-failure case for the calculator-blocked path. (gpt-5.5 fixes this by adding llm_failed: bool to state.)
    • Less code-level detail than gpt-5.5 or qwen-3.7-max — useful for review but somebody implementing it must still author the helper signatures.
    • The single decision_policy node will still be ~80 LOC and several concerns deep; the proposal acknowledges this implicitly but does not provide a sub-structure (e.g., named helper chain inside the node).

    Verdict: The most architecturally honest proposal. Best one to adopt as the structural baseline.

    #2 — gpt-5.5-proposal.md (most production-ready)¶

    Seven-node pipeline: enter_iteration → prepare_schema → require_region/require_currency → acquisition_gate → plan → normalize_decision → retry_gate → maybe_calculate → <action>.

    What is good:

    • Strict ownership tables for every node ("owns iteration lifecycle only", "owns deterministic state preparation", etc.) make node contracts unambiguous.
    • Adds llm_failed: bool (or decision_origin enum) to state — the cleanest way to preserve the current safeguard that a failed LLM finishes rather than getting redirected into reflect and failing again. This is a real defect that gpt-5.4, kimi-2.6, and opus-proposal do not address explicitly.
    • Explicitly resists adding prepared_recipes to state ("not unless serialization of FieldAcquisition is proven safe"). This is the right instinct — recipes is a derived cache, and several other proposals (deepseek-4-pro, qwen-3.7-max) add it to state without justifying serializer compatibility against MSGPACK_ALLOWLIST.
    • Test-mapping section is the most thorough of the set: every existing decision test in tests/planner/test_planner_decisions.py gets a target node.
    • Step 1 is "pure helper extraction without graph change" — the safest possible first commit.
    • Explicit non-goals prevent scope creep into the outer conversation graph and the PlannerDecision action enum.

    What is weak:

    • Splits normalize_decision and retry_gate and maybe_calculate into three separate post-LLM nodes. Functionally clean, but adds two extra checkpoint hops per iteration vs. gpt-5.4's single decision_policy. The "more nodes and edges" cost is acknowledged but not measured.
    • Splits require_region and require_currency into two distinct nodes rather than one parameterised require_core_field. Cosmetic redundancy.
    • The graph diagram becomes visually larger; reviewers must keep more node names in head.

    Verdict: Most precise and complete write-up; combines very well with gpt-5.4.

    #3 — deepseek-4-pro-proposal.md¶

    Four-node pipeline: guard → prepare → plan → adjust, with a self-loop on plan for post-LLM decomposition.

    What is good:

    • Smallest non-trivial split that still answers the problem: gates upfront, prep next, LLM minimal, corrections after.
    • Single adjust node for all post-LLM rewrites is the same correct call as gpt-5.4's decision_policy.
    • Self-loop on plan is a clever way to handle the case where the LLM targets a requires_components field that has no decomposition yet — re-prompt with augmented recipes. Most other proposals bury this in normalize_decision/enforce_policy.
    • Concrete line ranges and a trade-off table make the proposal easy to review against the source.
    • Tightest mapping between extracted blocks (846–887 → guard, 889–1035 → prepare, 1037–1088 → plan, 1090–1192 → adjust).

    What is weak:

    • Adds recipes to State without addressing the MSGPACK_ALLOWLIST / checkpointer compatibility concern that gpt-5.5 flagged explicitly. FieldAcquisition is a Pydantic type; storing it in state risks serializer churn.
    • Self-loop on plan doubles the LLM hit for composite-target cases — acceptable but worth flagging as a cost.
    • prepare carries calculator-cap + auto-complete + acquisition-task selection + composition — that is four concerns squeezed into one "prep" node, which is heavier than the name suggests.
    • The "guard rebuilds recipes" mitigation in the Risk section ("prepare and plan both rebuild recipes when decomps change") signals state-sync friction that the proposal does not fully resolve.

    Verdict: A clean middle-ground if you do not want six or seven nodes, with one genuinely novel idea (the plan self-loop) worth lifting into the recommended solution.

    #4 — glm-5.1-proposal.md¶

    Two-node pipeline: pre_check → acquire_or_plan → <action>. Keeps post-LLM rewriting inline in acquire_or_plan. Option B (extract validate_decision) is explicitly deferred.

    What is good:

    • Most conservative pragmatic option. Solves the worst part of the problem (pre-LLM guards become a graph-visible phase) without touching the post-LLM logic at all.
    • Honestly trades clarity for stability: keeps the migration small enough that planner-decision tests can be ported piece by piece.
    • Recognises that the "post-LLM rewriting" cluster is itself a coherent sub-concern, and proposes extracting it later (Phase 4) only if acquire_or_plan proves still too complex.
    • Identifies the loop-back edge change (plan → pre_check) as the key checkpoint-compatibility risk and proposes a test for resume-after-interrupt.
    • Concrete _build_plan_output helper proposal for collapsing the 9-way return pattern — orthogonal but useful.

    What is weak:

    • After phase 1, acquire_or_plan is still ~200 LOC. The graph is more honest at the front but unchanged at the back, so calculator-cap / search-cap / redirect tests still need broad fixtures.
    • _pre_check_route as a Literal[...] string field is workable but uglier than gpt-5.4's decision.action-based dispatch. The proposal also suggests extending the Action enum with guard variants and then rejects it, which is the right call but adds room for confusion.

    Verdict: The right migration if the team has low risk budget and wants to land Phase 1 quickly without committing to a six-stage redesign. Should be viewed as Phase 1 of gpt-5.4/gpt-5.5, not a competing endpoint.

    #5 — kimi-2.6-proposal.md¶

    Eight-node pipeline: tick → ask_region/ask_currency → prepare → calc_gate → acquire → route_direct → decide → enforce_policy → <action>.

    What is good:

    • Explicit decision matrix at the end (mapping every block in plan_node to its destination node + rationale) — very useful for implementers.
    • Splits bootstrap into dedicated ask_region/ask_currency nodes which makes the "structural, not LLM" nature of those questions visible on the graph.
    • route_direct adapter node is a smart way to converge deterministic-acquisition decisions and LLM decisions into the same enforce_policy pipeline without duplicating post-processing.
    • Concrete LOC estimates per node (decide ~30, prepare ~30, enforce_policy ~120). Useful sanity check.

    What is weak:

    • Bootstrap split is over-resolved. ask_region and ask_currency produce identical decision shapes (PlannerDecision(action="ask_user", ...)) with different field paths; one parameterised require_core_field node would express the same thing without graph noise.
    • route_direct is a single-purpose adapter node that exists only to bridge two upstream nodes into one downstream node. A direct edge with a shared post-processor would do the same job.
    • enforce_policy remains heavy (~120 LOC) with several rewrites + caps stitched together. Splitting the bootstrap but not the policy is an inverted priority — the bootstrap is structurally simple, the policy chain is where bugs hide.

    Verdict: Solid mid-tier. Some good ideas (decision matrix, route_direct adapter pattern) but the bootstrap split is graph-decorative.

    #6 — qwen-3.6-plus-proposal.md¶

    Six-ish-node pipeline: preflight → ask_region/ask_currency → observe_region/observe_currency → decompose → plan → route_finish_check → <action>. Moves post-LLM redirects into route_after_plan (an edge function, not a node).

    What is good:

    • route_finish_check is a sharp idea: today's finish edge does not validate that finishing is appropriate; this proposal inserts a check that can loop back to plan if work still remains.
    • Phase-by-phase migration with concrete _build_state_graph() snippets — easy to follow.
    • Decomposition becomes its own node rather than living inside either prep or plan. This matches the "decompose before planning, not during" mental model.

    What is weak (major issue):

    • Moves redirect logic and per-field cap enforcement into the edge function route_after_plan. This is the biggest single anti-pattern in any proposal. LangGraph conditional edges should be pure: read state, return a label. Putting _redirect_derived_direct_decision, _redirect_premature_ask_for_web_field, search-cap and ask-user-cap checks, and "logging" into a conditional-edge function violates the idiom that other proposals (notably gpt-5.4) flag explicitly. The redirects also mutate the decision, which is even worse — edges should not mutate.
    • Dedicated observe_region / observe_currency nodes duplicate the per-target dispatch that observe_user_node already handles via target_field switching. This adds two nodes and breaks the existing single-observe-user invariant.

    Verdict: Has one good idea (route_finish_check) wrapped in a serious idiomatic violation. The redirect-in-edge approach should not be adopted.

    #7 — qwen-3.7-max-proposal.md¶

    Ten-node pipeline: check_termination → check_region_currency → compose_schema → check_calculator → acquisition_routing → check_completion → llm_decide → post_process → enforce_caps → route_decision → <action>.

    What is good:

    • Most code-complete proposal: every node has a worked implementation, every routing function is sketched. Useful as an implementation reference.
    • Explicit transient state fields (_route, _llm_failed) marked as NotRequired[str] and excluded from checkpointing — addresses one of the concerns raised in gpt-5.5.
    • Recognises the route_finish_check problem that qwen-3.6-plus surfaced, and integrates it as check_completion.

    What is weak:

    • Per-node _route hint field on State is verbose: every guard node has to set _route and a separate routing function has to read it. This adds I/O at every edge for what is essentially a glorified return value. Other proposals (deepseek, gpt-5.4) achieve the same with a decision.action check or a small named routing function — cleaner.
    • Ten nodes is at the upper end of useful granularity. The graph diagram becomes harder to scan than the original problem; the gain over gpt-5.4's six nodes is marginal.
    • compose_schema and check_calculator are separated even though composition is a prereq for calculator state evaluation in the same iteration — a single prepare_context (per gpt-5.4) covers both.
    • Several state writes happen in routing/observation paths (route_decision does _emit_decision_event) — minor side-effect leak.

    Verdict: Good as a reference implementation source but over-decomposed. Pick its concrete code, not its graph shape.

    #8 — opus-proposal.md¶

    Roughly thirteen-node pipeline: g_iter_cap → g_region → emit_region → g_currency → emit_currency → enrich_schema → g_calc_caps → emit_calc_* → acquire → emit_acq/emit_auto_finish → plan_llm → c_target_decompose → c_redirect_derived → c_redirect_web → c_search_cap → c_ask_cap → c_calc_adjust → dispatch.

    What is good:

    • The cleanest theoretical decomposition: every concern is its own node with a single responsibility. The naming convention (g_* for gates, c_* for correctors) is helpful.
    • enrich_schema as a pure no-decision node is the right boundary.
    • Adds llm_failed: bool explicitly with documented read/write semantics.
    • Per-node "writes" table clarifies state ownership precisely.
    • Honestly acknowledges the cost of "up to 10 checkpointer hops per iteration" and proposes mitigation (use add_edge not add_conditional_edges where target is static).

    What is weak:

    • Too chatty for a production planner. Each conversation turn already costs an LLM call plus several search hops; multiplying the checkpoint writes by 10× per iteration is a real cost under PostgresSaver. The proposal's own mitigation ("use add_edge") admits the design's overhead.
    • c_* corrector chain is a straight-line add_edge chain — which is structurally identical to a single decision_policy node calling the same helpers in order. The "diagram becomes truthful" benefit is real but partly cosmetic.
    • The proposal itself flags this in its alternatives section: deepseek-4-pro's "deeper decomposition (16 nodes)" was rejected as "too chatty"; opus-proposal lands at 13 and runs into the same problem.

    Verdict: Architecturally elegant, operationally heavy. Useful as the limit of how far decomposition can go — but the right answer sits at the gpt-5.4 / gpt-5.5 level.

    #9 — mimo-2.5-pro-proposal.md¶

    Three-node pipeline: guards → acquire → decide → <action>. Post-LLM redirects and per-field caps stay inside decide.

    What is good:

    • Minimal, low-risk migration with a clean Phase-1 strategy (extract helpers without changing topology).
    • Open questions section at the end is honest about the unresolved trade-offs.

    What is weak:

    • Does not solve the problem. The whole point of the refactor is to expose hidden routing; decide ends up still owning the LLM call + all redirects + all cap enforcement. The proposal's own table shows decide at ~80 LOC, which is exactly the "god-node lite" trap.
    • acquire populates next_acquisition_task on state but the deterministic-acquisition-vs-LLM-call branch happens inside decide, not at the graph level. So the graph still shows guards → acquire → decide, hiding the deterministic short-circuit.
    • Three nodes is the same trap as the current architecture — just renamed.

    Verdict: Honest minimum, but not enough to justify the migration cost.

    #10 — gemini-3.1-pro-proposal.md¶

    Three-node pipeline: prepare_state → evaluate_rules → llm_plan → <action>.

    What is good:

    • Cleanest separation between "state mutation" (prepare_state) and "deterministic rules" (evaluate_rules) and "LLM call" (llm_plan). The conceptual split is good.
    • Concise and easy to read — one page of mermaid and three nodes.

    What is weak:

    • evaluate_rules becomes a new god-node: the proposal explicitly says it handles max_iters, aborted, region, currency, calculator status/caps, blocked-state acquisition, and auto-finish. That is six concerns interleaved in one function — the same anti-pattern, only smaller.
    • No post-LLM rewriting story. The redirects (_redirect_derived_direct_decision, _redirect_premature_ask_for_web_field, calculator adjustment, search/ask caps) are not mentioned at all. They presumably end up inside llm_plan — but that breaks the "LLM-only" framing the proposal asserts.
    • Returning None from evaluate_rules as the "needs LLM" signal is a workable pattern but the proposal does not specify how the routing function distinguishes "rule produced a decision" from "no rule fired" robustly.

    Verdict: A good sketch of the philosophy; insufficient as a migration plan. Useful for orientation but should not be adopted as-is.

    3. Synthesis: convergent agreements and divergent calls¶

    Where all proposals agree¶

    1. plan_node() must be split. None of the proposals defend the status quo.
    2. A pre-LLM "guard / preparation / bootstrap" phase belongs at the graph level, not inside the LLM node.
    3. The LLM node should shrink to prompt build + structured call + finish-on-LLM-failure, nothing else.
    4. Loop-back edges from action nodes (observe, calculate, reflect, observe_user) should re-enter the graph at the new top node (tick / guard / pre_check / enter_iteration), not at the LLM node.
    5. ask_user remains the single interrupting node.
    6. The outer conversation graph (route_if_needed → planner_step → persist) is out of scope.

    Where they diverge¶

    Decision point Conservative Middle Aggressive
    Node count for planning phase 2 (glm), 3 (mimo, gemini) 4 (deepseek), 6 (gpt-5.4), 6+ (qwen-3.6) 7 (gpt-5.5), 8 (kimi), 10 (qwen-3.7), 13 (opus)
    Bootstrap region/currency one gate (deepseek, glm) one node with branch (gpt-5.4, gemini) two dedicated nodes (kimi, qwen-3.6, opus)
    Post-LLM rewrites inline (glm, mimo, gemini) one policy node (gpt-5.4, deepseek) chain of corrector nodes (gpt-5.5, opus)
    Decomposition before plan inline (most) own node (qwen-3.6) as part of prepare_context (gpt-5.4)
    LLM-failure signal in state not addressed (gpt-5.4, deepseek, kimi, qwen, glm, mimo, gemini) llm_failed: bool (gpt-5.5, opus, qwen-3.7)
    Acquisition cache in state rebuilt per node (gpt-5.5) recipes/dynamic_decompositions in state (deepseek, qwen-3.7)
    Redirect placement inside the node edge function (qwen-3.6 — anti-pattern)

    The strong proposals stay in the middle column.

    4. Recommendation¶

    Adopt the structural shape of gpt-5.4-proposal.md plus two precise additions from gpt-5.5-proposal.md and one targeted idea from deepseek-4-pro-proposal.md.

    4.1 Structural baseline — gpt-5.4¶

    Six-phase pipeline:

    START → tick → bootstrap_gate → prepare_context → acquisition_gate → llm_plan → decision_policy → <action>

    All loop-back edges re-enter at tick. ask_user stays the single interrupt node. decision_policy is one node, not a corrector chain.

    4.2 Additions from gpt-5.5¶

    1. Add llm_failed: bool (or decision_origin: Literal["deterministic","llm","llm_error"]) to PlannerState. Without it, the calculator-blocked recovery path can redirect an LLM failure into reflect and re-fail. gpt-5.4 silently inherits this risk; gpt-5.5 fixes it explicitly.
    2. Do not add prepared_recipes / recipes to state (gpt-5.5's negative recommendation). Rebuild from dynamic_decompositions + static_field_acquisition in each node that needs them, until FieldAcquisition is proven compatible with MSGPACK_ALLOWLIST in checkpoint_serde.py. Deepseek-4-pro and qwen-3.7-max get this wrong.

    4.3 Targeted idea from deepseek-4-pro¶

    Keep the plan self-loop for the composite-target case. When llm_plan returns a decision targeting a requires_components field that has no decomposition yet, the cleanest place to generate a decomposition and re-prompt is a self-edge on llm_plan, not a corrector inside decision_policy. Other proposals stuff this into post-processing, which makes the LLM-decomposition LLM call invisible at the graph level. The deepseek self-loop exposes it.

    4.4 Staged migration (6 commits, each green)¶

    Reusing the gpt-5.4 sequence with one adjustment:

    Stage What Risk
    1 Extract tick (iteration + abort + max_iters). Rewire all loop-back edges from plan to tick. Low
    2 Extract bootstrap_gate (region + currency). Single node with internal branch; one decision per call. Low
    3 Extract prepare_context (proactive decompositions, recipe build, ready-field composition). Low–Medium
    4 Extract acquisition_gate (calculator caps, calculator success, blocked-calc next task, auto-finish). Medium
    5 Slim plan → llm_plan (LLM call only). Add llm_failed state field. Add plan → plan self-loop for composite-target decomposition. Medium
    6 Extract decision_policy (derived-redirect, web-preferred-redirect, search cap, ask-user cap, _adjust_calculation_decision). Medium

    After Stage 6, replace current-graph.md with the new mermaid and link this proposal as the accepted ADR. Update tests/planner/test_planner_decisions.py to target the appropriate node per case (see gpt-5.5 §"Tests to update or add").

    4.5 What to avoid from the other proposals¶

    • opus-proposal's 13-node corrector chain — too chatty for the value it adds.
    • qwen-3.6's redirect-in-edge-function pattern — violates LangGraph edge purity.
    • kimi-2.6's split bootstrap nodes — graph noise without semantic gain.
    • qwen-3.7-max's _route hint field on State — verbose dispatch; prefer decision.action-based routing.
    • mimo-2.5-pro and gemini-3.1-pro — under-decomposed; do not solve the original problem.

    5. Summary ranking¶

    Rank Proposal One-line verdict
    1 gpt-5.4-proposal.md Best architectural balance; adopt the six-phase shape.
    2 gpt-5.5-proposal.md Most precise write-up; harvest llm_failed state + test map + recipe-rebuild rule.
    3 deepseek-4-pro-proposal.md Clean four-phase split; harvest the plan self-loop idea.
    4 glm-5.1-proposal.md Right Phase-1 stop if risk budget is tight.
    5 kimi-2.6-proposal.md Solid; over-decomposes bootstrap.
    6 qwen-3.6-plus-proposal.md Good route_finish_check idea wrapped in an edge-purity violation.
    7 qwen-3.7-max-proposal.md Useful as a code reference; graph shape is over-resolved.
    8 opus-proposal.md Theoretically pure; operationally heavy.
    9 mimo-2.5-pro-proposal.md Honest minimum; does not actually solve the problem.
    10 gemini-3.1-pro-proposal.md Right philosophy, insufficient detail; evaluate_rules becomes a new god-node.

    Recommended path: gpt-5.4 structure + gpt-5.5 state hygiene + deepseek-4-pro self-loop — staged in six green commits per §4.4.
