    Planner Graph Refactor Proposals — Ranked Analysis¶

    Date: 2026-06-08
    Analyst: Sisyphus (kimi-k2.6)
    Scope: Evaluate 10 proposals for decomposing the monolithic plan_node in src/venturescope/planner/agent.py into graph-level nodes and conditional edges.
    Source Material: docs/planner-graph-ref/proposals/*.md, src/venturescope/planner/agent.py:846-1192, docs/planner-graph-ref/current-graph.md

    Executive Summary¶

    All 10 proposals agree on the core problem: plan_node is a ~350-line "god node" that conflates iteration bookkeeping, bootstrap questions, schema composition, calculator gating, deterministic acquisition routing, LLM planning, and post-LLM policy rewriting into a single function. The graph diagram is therefore misleading — route_after_plan is a trivial 4-line string dispatch because all real routing intelligence lives inside the node.

    The proposals diverge primarily on granularity: how many nodes to extract and which concerns to group together. After evaluating all 10 against the project's constraints (LangGraph + PostgresSaver checkpointer, real production traffic, staged migration necessity, existing test coverage), the recommended path is a hybrid of the deepseek-4-pro, gpt-5.4, and kimi-2.6 proposals — specifically a 5-node pipeline with a staged migration.

    Evaluation Criteria¶

    # Criterion Weight Why it matters for this project
    1 Granularity balance High Too coarse leaves the monolith alive; too fine adds checkpoint overhead and graph noise
    2 Migration safety High The planner is in the hot path of every conversation turn; must ship green at each stage
    3 Testability High Need clear seams for unit tests without mocking the entire 350-line function
    4 Checkpoint discipline High PostgresSaver writes state at every node boundary; extra hops = extra DB writes per iteration
    5 Observability Medium LangSmith/Mermaid should honestly reflect control flow
    6 State surface changes Medium Adding fields risks old-checkpoint compatibility; fewer changes = safer
    7 LangGraph idiomaticity Medium Nodes do work + write state; edges read state + return route labels; no state mutation in edges

    Proposal Rankings¶

    #1 — deepseek-4-pro-proposal.md ⭐ Best Overall¶

    Granularity: 4-node pipeline (guard → prepare → plan → adjust)
    Key insight: Separates gatekeeping, preparation, LLM planning, and policy correction into distinct phases. All action nodes loop back to guard, ensuring abort/max-iter checks run every cycle.

    Strengths: - Perfect granularity balance. 4 nodes is the sweet spot: enough to make each node testable and honest in the diagram, but not so many that checkpoint overhead becomes a concern. Each node has a clear, single responsibility. - Graph topology is clean and honest. The Mermaid diagram actually describes the control flow. guard short-circuits to ask_user or finish; prepare handles all schema/decomposition work; plan is purely LLM; adjust is purely policy correction. - Migration path is excellent. Phase 1 extracts helper functions without changing graph shape (zero risk). Phase 2 changes edges (medium risk, but tests exist). Phase 3 is cleanup. - Loop-back to guard is the right semantic choice. Every iteration should re-check abort/max-iter conditions. Current code does this manually inside plan_node; making it a graph-level invariant is safer. - Handles the _adjust_calculation_decision concern correctly. By routing auto-finish and acquisition-task decisions through adjust (not directly to action nodes), calculator rewrites still apply. This avoids duplicating _adjust_calculation_decision logic across multiple edges. - Adds recipes to state — actually useful. Today build_dynamic_recipes is called in at least 3 places (plan_node, observe_node, observe_user_node, reflect_node). Caching it in state avoids redundant recomputation.

    Weaknesses: - The adjust node is still ~80 lines and combines 5 different corrector functions. This is acceptable — it's a single "policy enforcement" responsibility — but could be further split later if it grows. - No explicit tick vs guard separation; iteration increment lives in guard. This is minor — guard is still small (~20 lines). - Does not explicitly address the "post-LLM decomposition generation loop" (lines 1072-1088 in current plan_node). The proposal says "loop back to itself" for the plan node, which is correct but could be clearer about implementation.

    Verdict: The most balanced proposal. It achieves the architectural goal (graph-level routing honesty) without over-engineering.

    #2 — gpt-5.4-proposal.md ⭐ Best Staged Migration¶

    Granularity: 6-node pipeline (tick → bootstrap_gate → prepare_context → acquisition_gate → llm_plan_node → decision_policy)
    Key insight: Explicitly separates tick (iteration lifecycle) from bootstrap_gate (region/currency), and introduces decision_policy as a single post-LLM normalization node.

    Strengths: - Best staged migration of all proposals. 6 explicit stages, each one adding a single seam. Stage 1 (tick extraction) is the lowest-risk first step imaginable. Each stage ships independently. - Explicit tick node is a good architectural choice. Having exactly one node that increments iterations prevents the drift risk mentioned in the proposal (attempt logs and turn-scoped search extraction depend on iteration counters). - decision_policy as one node is the right call. The proposal explicitly rejects splitting every redirect into separate nodes, calling it "graph noise." This shows mature judgment. - Very strong LangGraph discipline. Explicitly warns against state mutation in edge functions and against moving interrupts into policy gates. - Clear statement of what should NOT change. The "What should not change" section is exemplary — it scopes the refactor precisely.

    Weaknesses: - 6 nodes is approaching the upper limit of acceptable checkpoint overhead. Each node hop is a PostgresSaver write. With 50 max iterations, a conversation turn could trigger 50 × 6 = 300 checkpoint writes just for the planning phase. This is likely still fine (each write is small), but it is more than deepseek's 4 nodes. - bootstrap_gate as a separate node from tick adds a hop for every iteration even after bootstrap is complete. Region/currency are only relevant in the first 1-2 iterations; gating on them every cycle is slightly wasteful. The deepseek approach (putting them in guard) is more efficient. - The acquisition_gate name is slightly misleading. It handles both acquisition tasks AND auto-finish checks AND calculator gating. The deepseek prepare + acquisition_gate split is cleaner.

    Verdict: Excellent for teams that value maximum migration safety over absolute minimalism. The 6-stage rollout is the most defensible approach for a production system.

    #3 — kimi-2.6-proposal.md ⭐ Best Bootstrap Clarity¶

    Granularity: 8-node pipeline (tick → ask_region/ask_currency → prepare → calc_gate → acquire → route_direct/decide → enforce_policy)
    Key insight: Treats bootstrap questions as first-class graph nodes, not hidden early-returns. This makes the pre-flight loop visually explicit.

    Strengths: - Dedicated ask_region and ask_currency nodes are the clearest bootstrap representation. No other proposal makes the pre-flight loop this visually honest. For a system where region/currency anchoring is critical to search quality, this clarity has real operational value. - calc_gate as a separate conditional edge is elegant. Calculator success and cap are pure predicates; expressing them as graph transitions makes the "finish on success" path obvious. - route_direct is a good pattern. The tiny adapter node that bridges deterministic acquisition tasks into the post-processing pipeline avoids duplicating _adjust_calculation_decision logic. - Strong observability story. Per-node logging, timing, and retry hooks are natural when each node has a single responsibility. - Excellent appendix decision matrix. The "What Goes Where" table is the clearest mapping of all proposals.

    Weaknesses: - 8 nodes is definitely on the high side for checkpoint overhead. Every iteration goes through tick → prepare → calc_gate → acquire → [route_direct|decide] → enforce_policy. That's 6 hops per iteration × 50 iterations = 300 writes. The dedicated ask_region/ask_currency nodes add complexity for a concern that is only relevant in the first 1-2 iterations. - Loop-back to tick instead of guard means calc_gate runs on every iteration even when aborted or max-iter exceeded. The deepseek approach (loop back to guard, which checks abort FIRST) is safer. - enforce_policy is still the most complex node (~80 lines). This is acknowledged in the proposal, but it's the same complexity as deepseek's adjust — no worse, no better.

    Verdict: Best choice if the team values explicit bootstrap handling and operational visibility over raw checkpoint efficiency. The dedicated bootstrap nodes are a genuine architectural win for systems with mandatory pre-flight fields.

    #4 — glm-5.1-proposal.md¶

    Granularity: 2 main nodes (pre_check → acquire_or_plan)
    Key insight: The minimal viable decomposition — split only the guard/prerequisite phase from the LLM + policy phase.

    Strengths: - Lowest migration risk of all proposals. Only one new node (pre_check) and one graph edge change. The rest of the logic stays in a single node. - _build_plan_output helper is a good idea. Collapsing the 9-way conditional-return pattern into a single helper reduces code duplication without changing graph topology. - Realistic about what can be extracted in one pass. The proposal acknowledges that acquire_or_plan will still be ~200 lines and recommends Option A (keep post-LLM rewriting inline) for the first pass. - Explicitly warns against over-splitting. The rejected alternatives (deeper decomposition, minimal change, calculator subgraph) show good judgment.

    Weaknesses: - Too conservative. acquire_or_plan at ~200 lines is still a substantial monolith. The whole point of the refactor is to make the graph honest and testable; leaving 60% of the logic in one node only partially achieves that. - The pre_check node still mixes too many concerns. It handles iteration increment, abort, max-iter, region, currency, calc cap, calc success, AND proactive decomposition. That's 7 responsibilities in one node. - Uses a dedicated _pre_check_route state field. This is slightly clunky — deepseek and gpt-5.4 use decision + conditional edges naturally without extra routing fields. - Does not address the post-LLM corrector chain at all in Phase 1. The decision rewrites remain buried in acquire_or_plan.

    Verdict: A safe incremental step, but too timid for the stated goal of making the graph topology reflect actual control flow. Would be acceptable as a Phase 1 only, with further decomposition planned.

    #5 — mimo-2.5-pro-proposal.md¶

    Granularity: 3-node pipeline (guards → acquire → decide)
    Key insight: A middle-ground decomposition: guards, then acquisition/deterministic routing, then LLM + post-processing.

    Strengths: - Simple and easy to understand. Only 3 new nodes and 2 new routing functions. The mental model is straightforward. - Loop-back to guards is correct. Ensures early-exit conditions are checked every iteration. - guards node captures the most important short-circuits. Abort, max-iter, region, currency — the gates that most often skip LLM planning. - Migration path is sensible. Phase 1 extracts without topology change; Phase 2 wires into graph; Phase 3 cleans up.

    Weaknesses: - decide node is still ~80 lines and combines LLM call + 5 corrector functions. This is the same critique as glm-5.1 — the post-LLM phase remains monolithic. - acquire node mixes schema preparation with deterministic routing. Proactive decomposition, recipe building, field composition, blocked-calc acquisition, AND auto-finish checks all live in one node. That's 5 concerns. - No explicit adjust/policy node. The post-LLM rewrites (derived redirect, web-pref redirect, search cap, ask cap, calc adjust) are all inside decide. This means the graph still hides significant routing intelligence. - Less explicit about calculator gating than deepseek/gpt-5.4. The calculator cap/success checks are inside guards, which is fine, but the interaction with _adjust_calculation_decision is less clear.

    Verdict: A decent middle-ground, but the lack of a dedicated post-LLM policy node means the graph still isn't fully honest. Would be improved by splitting decide into llm_plan + policy.

    #6 — gemini-3.1-pro-proposal.md¶

    Granularity: 3-node pipeline (prepare_state → evaluate_rules → llm_plan)
    Key insight: Separates state mutation, deterministic rule evaluation, and LLM planning into three clean layers.

    Strengths: - Conceptually elegant separation. prepare_state = pure transformation; evaluate_rules = deterministic routing; llm_plan = heuristic/LLM routing. This is a clean layered architecture. - Action nodes loop back to prepare_state instead of plan. This is correct because schema/decomposition may have changed during the action, and prepare_state recomposes them. - Very concise and readable. The proposal is only 117 lines but covers the full topology.

    Weaknesses: - evaluate_rules would still be a large node. It handles max-iter, abort, region, currency, calculator caps, calculator success, blocked-calc acquisition, auto-finish, AND open-task selection. That's ~8 responsibilities in one node — essentially the top half of today's plan_node. - No explicit post-LLM policy node. Corrector functions stay inside llm_plan or are not mentioned. The graph therefore still hides redirect/cap logic. - Action nodes loop back to prepare_state rather than evaluate_rules. This means prepare_state runs on every iteration even when the schema hasn't changed. Slightly wasteful; looping back to a guard/tick node that checks abort first would be more efficient. - Lacks migration staging detail. The implementation steps are correct but don't address checkpoint compatibility risks or test migration.

    Verdict: Good conceptual separation, but evaluate_rules is too large to be the single "deterministic routing" node. Would benefit from splitting evaluate_rules into guard + acquisition_gate as in deepseek/gpt-5.4.

    #7 — qwen-3.6-plus-proposal.md¶

    Granularity: 6 main nodes (preflight → ask_region/ask_currency → decompose → plan → route_finish_check)
    Key insight: Unique approach — moves post-LLM redirects INTO the route_after_plan conditional edge function rather than a node.

    Strengths: - preflight as a single guard node is clean. It replaces lines 852-943 (abort, max-iter, region, currency, calculator checks) with one well-named node. - route_after_plan gaining redirect logic is an interesting idea. The proposal correctly identifies that _redirect_derived_direct_decision, _redirect_premature_ask_for_web_field, _adjust_calculation_decision, and cap enforcement are all "routing" concerns, and suggests moving them to the edge function. - route_finish_check is a thoughtful addition. Validates that finish is actually appropriate before allowing END, which catches cases where the LLM prematurely declares completion. - No new state fields needed. Uses existing fields for all routing conditions.

    Weaknesses: - Moving redirects into edge functions violates LangGraph idioms. Edge functions should be pure predicates that return a string. The proposal's route_after_plan would need to perform decision mutation (rewriting action, target_field, search_query, etc.), which means either: a) Edge functions mutate state (anti-pattern, hard to debug, checkpoint surprises), or b) The edge function returns a modified decision as a side-channel, which LangGraph doesn't support naturally. - route_after_plan would be ~100 lines of complex logic. This doesn't solve the monolith problem — it just moves it from a node to an edge function, where it's even harder to test and observe. - ask_region/ask_currency loop back to preflight, not observe_user. The current observe_user_node handles region/currency answers via target-field checks. The proposal introduces dedicated observe_region/observe_currency nodes, which adds 2 more nodes and 2 more edges for a concern that's already handled cleanly. - No staged migration plan. The phases are listed but don't address checkpoint compatibility or test migration risks.

    Verdict: The edge-function approach for redirects is architecturally questionable. Edge functions should be simple predicates; complex decision rewriting belongs in nodes. The route_finish_check idea is good, but the core routing strategy is a step backward.

    #8 — opus-proposal.md¶

    Granularity: 12+ nodes (g_iter_cap → g_region → g_currency → enrich → g_calc_caps → acquire → plan_llm → c_target_decompose → c_redirect_derived → c_redirect_web → c_search_cap → c_ask_cap → c_calc_adjust → dispatch)
    Key insight: Maximum decomposition — every gate and every corrector gets its own node. The c_* corrector chain is a straight line of nodes with no branching.

    Strengths: - Most honest Mermaid diagram of all proposals. Every gate and every corrector is visible. Reading the diagram actually tells you the full policy. - dispatch as a canonical decision-log + route point is a good pattern. Consolidates the 3 distinct log.bind(...).info(...) sites in today's plan_node into one place. - Explicit llm_failed transient flag is useful. Prevents the corrector chain from redirecting a failed LLM output into reflect, which would create an infinite loop. - Node-by-node mapping table is the most detailed of all proposals. 17 rows, each mapping old lines to new nodes. - g_* gate naming convention is helpful. Makes it immediately obvious which nodes are pure predicates vs. work nodes.

    Weaknesses: - Severe checkpoint overhead. A typical iteration goes through: g_iter_cap → g_region → g_currency → enrich → g_calc_caps → acquire → plan_llm → c_target_decompose → c_redirect_derived → c_redirect_web → c_search_cap → c_ask_cap → c_calc_adjust → dispatch. That's 14 hops per iteration × 50 iterations = 700 checkpoint writes. Even if each write is small, this is a 10× increase over the current 1 hop per iteration. - The c_* corrector chain adds nodes with zero branching value. c_target_decompose → c_redirect_derived → c_redirect_web → c_search_cap → c_ask_cap → c_calc_adjust is a straight line. Since there are no conditional edges between them, they could just as well be a single adjust node (as in deepseek) without losing any architectural clarity. The proposal acknowledges this: "c_* correctors form a straight add_edge chain — no predicates, no branching." - Splitting "emit" nodes (emit_region, emit_calc_abort, etc.) from gate nodes is overkill. g_region checks the predicate; emit_region creates the PlannerDecision. These are 2-3 lines each. Having them as separate nodes adds checkpoint hops for no benefit. - Migration risk is very high. 12 new nodes, 6 new routing functions, and a completely different graph topology. Step 2 alone ("hoist gates into graph") changes 6 node boundaries simultaneously.

    Verdict: An excellent academic decomposition, but impractical for a production system using PostgresSaver. The corrector chain should be collapsed into a single adjust/policy node. Adopt the gate naming convention and the dispatch pattern, but not the full 12-node topology.

    #9 — gpt-5.5-proposal.md¶

    Granularity: 10-node pipeline (enter_iteration → prepare_schema → require_region → require_currency → acquisition_gate → plan → normalize_decision → retry_gate → maybe_calculate)
    Key insight: Very granular decomposition with dedicated nodes for normalization, retry policy, and calculator routing.

    Strengths: - normalize_decision as a dedicated node is good. Post-LLM redirects (derived, web-pref, decomposition generation) have a clear home. - retry_gate makes per-field caps visible in the graph. This is a genuine architectural improvement over burying them in plan_node. - maybe_calculate explicitly handles the finish→calculate rewrite. This is the clearest calculator routing representation of all proposals. - Strong test migration guidance. Explicitly lists which test assertions should move to which new nodes.

    Weaknesses: - 10 nodes is excessive for checkpoint overhead. Same concern as opus and qwen-3.7-max: every iteration goes through ~8-9 hops. - require_region and require_currency as separate nodes from ask_user is questionable. They create the same interrupt payload as ask_user. Having them as dedicated nodes means the graph has special-case branches for what is fundamentally the same action. The kimi-2.6 approach (dedicated bootstrap nodes that route to observe_user) is similar but at least acknowledges this is for explicitness. - The graph shape is complex. normalize_decision → retry_gate → maybe_calculate is a 3-node post-LLM pipeline with conditional edges between each. This is harder to follow than deepseek's single adjust node. - No explicit guard/tick node for iteration lifecycle. enter_iteration handles iteration increment but doesn't check abort/max-iter before prepare_schema. The deepseek guard approach is safer.

    Verdict: Good ideas individually (normalize_decision, retry_gate, maybe_calculate), but the overall graph is too fragmented. These concepts would work better as helper functions inside a single adjust node, or as a smaller 5-6 node pipeline.

    #10 — qwen-3.7-max-proposal.md¶

    Granularity: 10+ nodes (check_termination → check_region_currency → compose_schema → check_calculator → acquisition_routing → check_completion → llm_decide → post_process → enforce_caps → route_decision)
    Key insight: Maximum decomposition with explicit guard nodes for every major check, plus a final route_decision dispatcher.

    Strengths: - Most comprehensive node-level testability. Every single check (termination, region/currency, calculator, completion, caps) is an independently testable node. - route_decision as a final dispatcher that also emits events is clean. One canonical place for decision logging before action execution. - Explicit post_process and enforce_caps separation is good. The post-LLM phase is split into decomposition/redirects and cap enforcement. - Full graph construction code provided. The _build_state_graph() sketch is the most complete of all proposals.

    Weaknesses: - Highest checkpoint overhead of all proposals. 10+ nodes per iteration, with many conditional edges. The graph is essentially re-implementing the plan_node if-else chain as a graph, but each branch is now a node boundary with a checkpoint write. - acquisition_routing and check_completion are sequential and have no real branching between them. They could easily be one node. Splitting them adds a hop for no architectural benefit. - The _route and _llm_failed transient state fields are clunky. These are essentially side-channels to pass information between nodes. The deepseek approach (using decision and natural conditional edges) avoids this. - The graph is harder to understand than the original code. A 10-node pipeline with 8 routing functions is more cognitive load than a 350-line function with early returns. The goal of the refactor is to reduce cognitive load; this proposal increases it. - No staged migration. The "Phase 1-5" migration plan exists but each phase introduces multiple nodes simultaneously.

    Verdict: Over-decomposed. The individual nodes are well-designed, but the aggregate graph is too fragmented to be maintainable. The checkpoint overhead and cognitive load outweigh the testability benefits.

    Recommended Approach: The "VentureScope Pipeline"¶

    After evaluating all 10 proposals, the recommendation is a hybrid approach that combines the best elements from the top 3 proposals:

    Final Graph Topology (5 nodes)¶

    flowchart TD
    planner_start([START]) --> guard[guard]

    guard -->|action=ask_user, region/currency missing| ask_user
    guard -->|aborted or max_iters| finish
    guard -->|continue| prepare[prepare]

    prepare -->|calculator_cap_exhausted or calc_success| finish
    prepare -->|blocked_task or auto_finish| adjust[adjust]
    prepare -->|continue| plan[plan]

    plan -->|decomposition needed| plan
    plan -->|continue| adjust

    adjust -->|search| search[search]
    adjust -->|ask_user| ask_user
    adjust -->|calculate| calculate[calculate]
    adjust -->|reflect| reflect[reflect]
    adjust -->|finish| finish

    search -->|last_observation present| observe[observe]
    search -->|no hits or backend failure| guard

    observe --> guard
    calculate --> guard
    ask_user --> observe_user[observe_user]
    observe_user --> guard
    reflect --> guard
    finish --> planner_end([END])

    Node Definitions¶

    1. guard (from deepseek-4-pro + gpt-5.4 tick)
    2. Increment iterations (exactly once per iteration)
    3. Check status == "aborted" → finish
    4. Check iterations > max_iters → finish
    5. Check _needs_region_question() → ask_user (region)
    6. Check _needs_currency_question() → ask_user (currency)

    7. Emit planning-step progress event

    8. prepare (from deepseek-4-pro)

    9. _proactive_decompositions(...)
    10. build_dynamic_recipes(...) → cache recipes in state
    11. compose_ready_fields(...)
    12. Calculator cap/success checks → finish
    13. Blocked-calc acquisition task selection → adjust
    14. Auto-finish + open-task acquisition selection → adjust

    15. Returns: updated schema, dynamic_decompositions, recipes

    16. plan (from deepseek-4-pro, gpt-5.4 llm_plan_node)

    17. Build planner_prompt(...) with full context
    18. Call _llm().structured(..., schema=PlannerDecision)
    19. On LLM failure → finish decision + llm_failed flag
    20. If LLM targets requires-components field without decomposition → generate decomposition and loop back to self

    21. Returns: raw decision, possibly dynamic_decompositions

    22. adjust (from deepseek-4-pro + gpt-5.5 normalize_decision/retry_gate/maybe_calculate as helpers)

    23. _redirect_derived_direct_decision()
    24. _redirect_premature_ask_for_web_field()
    25. Search cap / duplicate query detection → ask_user or reflect
    26. Ask-user cap detection → finish
    27. _adjust_calculation_decision() (finish→calculate, blocked→reflect)
    28. Log + emit final decision event

    29. Returns: corrected decision, possibly updated status

    30. dispatch (from opus-proposal, as edge function)

    31. route_after_adjust(state) reads decision.action and routes to action nodes
    32. Keeps the current route_after_plan contract but reads from adjust output

    Why This Hybrid?¶

    Decision Source Proposal Rationale
    5 nodes deepseek-4-pro + gpt-5.4 4-6 nodes is the sweet spot for checkpoint overhead vs. clarity
    guard + prepare split deepseek-4-pro Separates iteration/bootstrap from schema preparation; both are deterministic but different lifecycles
    plan loops to self for decomposition deepseek-4-pro Correctly handles the requires-components decomposition case without extra nodes
    Single adjust node deepseek-4-pro Collapses the opus/gpt-5.5 corrector chain into one policy node; 5 corrector functions as helpers inside one node is the right granularity
    recipes in state deepseek-4-pro Avoids redundant build_dynamic_recipes calls across nodes
    llm_failed flag opus-proposal, gpt-5.5 Prevents infinite reflect loops when LLM structured output fails
    Loop back to guard deepseek-4-pro, mimo-2.5 Ensures abort/max-iter checks run every cycle; safest semantic
    Staged migration (6 phases) gpt-5.4 Maximum production safety; each phase ships independently

    Conclusion¶

    Adopt the deepseek-4-pro decomposition as the primary architecture, with gpt-5.4's staged migration discipline and kimi-2.6's explicit bootstrap handling incorporated into the guard node. The target is a 5-node pipeline (guard → prepare → plan → adjust → dispatch) that balances:

    1. Graph honesty — the Mermaid diagram shows real control flow
    2. Checkpoint efficiency — ~4-5 hops per iteration, not 10+
    3. Testability — each node is 20-80 lines with a single responsibility
    4. Migration safety — 7 shippable stages, each with green tests
    5. LangGraph discipline — nodes do work and write state; edges read state and return labels

    The proposals ranked #8-10 (opus, gpt-5.5, qwen-3.7-max) contain excellent individual ideas (the dispatch pattern, llm_failed flag, maybe_calculate gate) but are over-decomposed as complete architectures. The proposals ranked #4-7 (glm-5.1, mimo-2.5, gemini-3.1, qwen-3.6-plus) are safe but too conservative or architecturally questionable. The top 3 (deepseek-4-pro, gpt-5.4, kimi-2.6) all represent good solutions; the hybrid above synthesizes their best aspects.
