    Planner Graph Refactor Proposals — Ranged Analysis¶

    Date: 2026-06-08 Author: Sisyphus (qwen-3.6-plus) Scope: docs/planner-graph-ref/proposals/ — 10 proposals evaluated against src/venturescope/planner/agent.py:846-1192

    Evaluation Criteria¶

    Criterion What it measures
    Granularity Node count vs. clarity — too few hides logic, too many creates graph noise
    Migration safety Phased approach, test preservation at each step, checkpoint compatibility
    State discipline Minimal schema changes, no state mutation in edge functions, no transient checkpoint pollution
    LangGraph alignment Nodes do work, edges route; conditional edges are pure predicates
    LLM isolation The LLM call is separated from deterministic gates
    Over-engineering risk Does the proposal split every if into its own node?
    Correctness Preserves current semantics (interrupt/resume, attempt tracking, calculator lifecycle)

    Ranked Proposals¶

    Rank 1 — gpt-5.4-proposal ⭐ BEST OVERALL¶

    Nodes: tick → bootstrap_gate → prepare_context → acquisition_gate → llm_plan → decision_policy (6 nodes replacing plan)

    Strengths: - Sweet-spot granularity. Six nodes is enough to expose every major lifecycle phase without exploding the graph into noise. Each node has a clear, non-overlapping responsibility. - Explicit anti-patterns section. Warns against moving state mutation into edge functions, incrementing iterations in multiple nodes, turning every policy rule into a node, and moving interrupts into policy gates. This shows deep understanding of LangGraph pitfalls. - Staged migration (6 stages) is the most disciplined of all proposals. Each stage ships green tests before the next begins. Stage 1 (extract tick) is the cleanest first seam with minimal checkpoint churn. - decision_policy as one node is the right call. Splitting every redirect (derived, web-preferred, search cap, ask cap, calc adjust) into separate nodes would add graph hops without improving clarity — this proposal explicitly rejects that. - Preserves outer contract. run_planner_step(), planner_thread_id(), ask_user interrupt behavior — all unchanged. - Attempt tracking awareness. Explicitly notes that only tick should change iterations to avoid drift with attempt logs in search_node(), observe_user_node(), and reflect_node().

    Weaknesses: - decision_policy at ~80 lines is still the most complex node, but this is an intentional trade-off acknowledged in the proposal. - The Mermaid graph shows acquisition_gate → decision_policy and llm_plan → decision_policy converging, which means decision_policy handles both deterministic and LLM-originated decisions — needs careful internal branching.

    Verdict: Best balance of clarity, safety, and LangGraph idiomaticity. The explicit anti-patterns list alone makes this the most implementation-ready proposal.

    Rank 2 — glm-5.1-proposal¶

    Nodes: pre_check → acquire_or_plan (2 nodes replacing plan)

    Strengths: - Minimal surface change. Only 2 new nodes means the graph topology change is small and the migration risk is low. acquire_or_plan at ~200 LOC is still a reduction from ~350. - Excellent implementation plan. Four phases with clear deliverables. Phase 3's _build_plan_output helper to collapse the 9-way conditional-return pattern is a practical improvement that all proposals should adopt. - Post-LLM rewriting options. Explicitly presents Option A (keep inline) vs. Option B (extract validate_decision node) with a reasoned recommendation to start with A. This pragmatism is rare. - State schema discipline. Proposes _pre_check_route as a separate field rather than polluting the Action enum with guard-only variants. Keeps Action clean. - Before/after comparison is concrete: "1 node, ~350 LOC, 9 return paths, 7 interleaved concerns" → "2 nodes, ~150 + ~200 LOC, clear separation."

    Weaknesses: - Least decomposition. acquire_or_plan still contains the LLM call, acquisition logic, AND all post-LLM rewriting. The LLM is not fully isolated. - _pre_check_route as a state field adds a transient key that flows through checkpoints. - Loop-back edges all go to pre_check, which means every iteration re-runs decomposition and composition even when short-circuiting — minor performance concern.

    Verdict: Safest migration path. Good for a first PR that proves the concept. But doesn't go far enough for the long-term target shape.

    Rank 3 — opus-proposal¶

    Nodes: g_iter_cap → g_region → g_currency → enrich_schema → g_calc_caps → acquire → plan_llm → c_target_decompose → c_redirect_derived → c_redirect_web → c_search_cap → c_ask_cap → c_calc_adjust → dispatch (14 nodes)

    Strengths: - Most thorough node-by-node mapping. Every line range in the current plan_node is mapped to a specific new node. No ambiguity about where code goes. - Gate/corrector naming convention. g_* for guards, c_* for correctors — makes the graph self-documenting. - Three-step migration is well-structured: extract helpers → hoist gates → split correctors. - State write ownership table is excellent. Each node's write surface is explicitly documented, eliminating the "who writes what" ambiguity that plagues multi-node graphs. - dispatch as canonical log point consolidates 3 distinct log.bind(...).info(...) sites.

    Weaknesses: - Most aggressive decomposition. 14 nodes (up from 1) is excessive. The corrector chain (c_target_decompose → c_redirect_derived → c_redirect_web → c_search_cap → c_ask_cap → c_calc_adjust) adds 6 graph hops per iteration, each triggering a checkpointer write under PostgresSaver. The proposal acknowledges this but dismisses it as "small" — for a hot-path planner running on every conversation turn, this is measurable overhead. - Splitting every corrector into its own node violates the principle that each node should have meaningful work. _redirect_derived_direct_decision is a single function call — making it a graph node is indirection, not decomposition. - Region/currency as separate gate nodes (g_region, g_currency) each with their own emit node adds 4 nodes for what is essentially two if checks.

    Verdict: Best documentation quality, worst granularity. The node-by-node mapping is invaluable as a reference, but the actual graph should merge the corrector chain into one decision_policy node (as gpt-5.4 proposes).

    Rank 4 — qwen-3.7-max-proposal¶

    Nodes: check_termination → check_region_currency → compose_schema → check_calculator → acquisition_routing → check_completion → llm_decide → post_process → enforce_caps → route_decision (10 nodes)

    Strengths: - Most detailed. Includes actual code samples for every node function and routing function. This is the most implementation-ready in terms of "you could start coding from this." - Clear node categorization. Guard nodes, transformation nodes, LLM node — the taxonomy is helpful. - _route transient field pattern is consistent across all nodes.

    Weaknesses: - _route in state is a checkpoint pollution risk. The proposal says "excluded from checkpointing" but LangGraph's PostgresSaver serializes the full state dict. There's no built-in mechanism to exclude fields. This would require custom serialization logic. - 10 nodes is too many. check_termination, check_region_currency, check_calculator, check_completion — four guard nodes that could reasonably be two. - observe_user → check_region_currency as the loop-back edge is inconsistent. Other action nodes loop to check_termination. This means region/currency questions skip termination checks on resume — a subtle behavioral change. - Code samples are verbose. Many nodes duplicate the current plan_node logic verbatim, which means the proposal is more "restate the code as nodes" than "design a better architecture."

    Verdict: Excellent as a coding reference, but the architecture is over-decomposed and the _route state pattern is risky for checkpointing.

    Rank 5 — deepseek-4-pro-proposal¶

    Nodes: guard → prepare → plan → adjust (4 nodes replacing plan)

    Strengths: - Clean 4-node pipeline. guard → prepare → plan → adjust is intuitive and maps well to the actual execution order. - Alternatives considered section. Explicitly rejects 16-node decomposition, keep-plan-node-with-edges, calculator subgraph, and extract-only-guard. Shows good judgment. - recipes in state is a practical addition that avoids redundant recomputation. - Migration is 4 phases with clear test verification at each step.

    Weaknesses: - prepare at ~50 lines still handles decomposition, recipe building, field composition, calculator lifecycle checks, blocked calculator acquisition, AND auto-completeness. That's 6 concerns in one node — the proposal acknowledges this but doesn't address it. - guard re-entry from all action nodes means every loop iteration re-runs region/currency checks even after they've been answered. This is correct but slightly wasteful. - adjust at ~80 lines handles all post-LLM rewriting — same concern as gpt-5.4's decision_policy, but without the explicit justification for keeping it as one node. - The Mermaid graph has search → guard but observe → guard — this means failed searches skip observe, which is correct, but the graph is harder to read than proposals that loop back to a single entry point.

    Verdict: Solid middle-ground proposal. The 4-node pipeline is clean but prepare is still doing too much.

    Rank 6 — mimo-2.5-pro-proposal¶

    Nodes: guards → acquire → decide (3 nodes replacing plan)

    Strengths: - Simplest decomposition. 3 nodes is the minimum meaningful split. Low risk, easy to understand. - Phase 1 keeps plan_node as orchestrator. This is the safest migration pattern — extract functions first, wire into graph second, delete old code last. - Clear metrics table. LOC, branching depth, testability — all quantified.

    Weaknesses: - Doesn't isolate the LLM. decide node handles both acquisition task conversion AND the LLM call AND all post-LLM redirects AND cap enforcement. The LLM is buried inside a node with 4 other responsibilities. - decide at ~80 lines is optimistic — the current post-LLM rewriting alone is ~120 lines. - plan_router as a node (mentioned in the graph but not described) is confusing. Is it a node or a routing function? - Least benefit. If the goal is to make the graph diagram truthful, 3 nodes still hides most of the routing intelligence inside decide.

    Verdict: Good as a first step, but not the target shape. The proposal itself acknowledges this with its open question about whether loop/cap detection should be a separate node.

    Rank 7 — gemini-3.1-pro-proposal¶

    Nodes: prepare_state → evaluate_rules → llm_plan (3 nodes replacing plan)

    Strengths: - Clear problem statement. Identifies the ~150-line procedural waterfall before the LLM is called. - evaluate_rules returns None or a decision. The "needs_llm" flag pattern is clean. - Good benefit summary. LangSmith visibility, LLM isolation, test seams — all valid.

    Weaknesses: - No migration plan. Just "refactor functions, update edges, rebuild graph." No phased approach, no risk assessment. - evaluate_rules is underspecified. It handles max_iters, region/currency, calculator status, acquisition tasks, AND auto-finish — that's 5 concerns in one node. - No discussion of state changes. What happens to decision when evaluate_rules sets it? How does route_after_rules know whether to route to llm_plan or an action node? - Shortest proposal (117 lines). Lacks the depth needed for a safe refactor of a hot-path component.

    Verdict: Good high-level idea, insufficient detail for implementation. The 3-node split is reasonable but the proposal doesn't earn its place higher due to lack of migration planning and state discipline analysis.

    Rank 8 — kimi-2.6-proposal¶

    Nodes: tick → ask_region/ask_currency → prepare → calc_gate → acquire → route_direct → decide → enforce_policy (8 nodes, with 2 being region/currency variants)

    Strengths: - Decision matrix appendix. Clear table mapping every logic block from current location to proposed location with reasoning. - route_direct as adapter node. Bridges deterministic acquisition tasks into the same post-processing pipeline as LLM decisions — good design. - Phased migration with helper extraction first, then graph registration, then cleanup.

    Weaknesses: - tick routes to needs_region | needs_currency as separate destinations, but these are handled by dedicated ask_region/ask_currency nodes. This adds 2 nodes for what could be a single bootstrap_gate node with conditional routing. - calc_gate as a separate node is reasonable, but acquire still handles both blocked-calc acquisition AND generic acquisition AND auto-finish — 3 concerns. - enforce_policy is still the most complex node at ~120 lines, handling all post-LLM rewriting. The proposal acknowledges this but doesn't offer a path to reduce it. - The "legacy compat" wrapper (plan_node as thin delegator) is mentioned but not well integrated into the migration plan.

    Verdict: Good structural thinking with the decision matrix, but the node count is high and the migration plan has gaps.

    Rank 9 — qwen-3.6-plus-proposal¶

    Nodes: preflight → ask_region → ask_currency → decompose → plan → route_finish_check (6 nodes, with 2 being region/currency variants)

    Strengths: - route_finish_check as a validation node. Prevents blind finish → END by checking caps and missing fields first. This is a safety improvement over the current graph. - 5-phase migration is well-structured. - What changes vs. what stays table is clear and actionable.

    Weaknesses: - Separate ask_region/ask_currency nodes are overkill. The region/currency checks are two if statements that could live in a single bootstrap_gate node with conditional edges. - decompose as a node is debatable. If decomposition always runs exactly once before planning, keeping it inside plan (as the first action) avoids a graph hop. The proposal acknowledges this in open questions but doesn't resolve it. - Post-LLM redirects move to route_after_plan (a routing function). Routing functions should be pure predicates — embedding redirect logic (which mutates decision) in a routing function violates LangGraph best practices. - observe_region/observe_currency as separate nodes removes the special-case branching from observe_user_node, but adds 2 more nodes for minimal benefit.

    Verdict: Good ideas (especially route_finish_check), but the post-LLM redirect-in-routing-function pattern is a LangGraph anti-pattern, and the region/currency node explosion adds unnecessary complexity.

    Rank 10 — gpt-5.5-proposal¶

    Nodes: enter_iteration → prepare_schema → require_region → require_currency → acquisition_gate → plan → normalize_decision → retry_gate → maybe_calculate (9 nodes)

    Strengths: - Most comprehensive consequences section. Positives, negatives, non-goals — all well articulated. - decision_origin state field ("deterministic" | "llm" | "llm_error") is a clean way to track decision provenance. - Test migration guidance is specific: which existing tests map to which new nodes. - Non-goals section is explicit and valuable.

    Weaknesses: - Most nodes (9). require_region and require_currency as separate nodes, normalize_decision and retry_gate as separate nodes — this is over-decomposition. - maybe_calculate as a node is questionable. Calculator routing is a simple predicate; making it a node adds a checkpoint write for what is essentially an if statement. - The Mermaid graph is the most complex of all proposals. Reading it requires tracing through 9 nodes to understand the control flow — arguably harder than reading the current plan_node function. - Migration has 4 steps but step 2 ("add graph nodes one group at a time") introduces 7 new nodes across multiple sub-steps, making it hard to ship green tests at each sub-step.

    Verdict: Best documentation hygiene (consequences, non-goals, test mapping), but the graph is too complex. The proposal contradicts its own goal of making the graph easier to understand.

    Synthesis: Recommended Approach¶

    No single proposal is perfect. The best implementation combines elements from the top-ranked proposals:

    Target Node Count: 5-6 nodes¶

    Node Responsibility Source
    tick Iteration increment, abort/max_iters check gpt-5.4
    bootstrap_gate Region/currency prerequisite questions gpt-5.4 (merged from qwen-3.6-plus's separate nodes)
    prepare_context Decomposition, recipe building, schema composition gpt-5.4
    acquisition_gate Calculator guards, blocked-calc acquisition, auto-finish gpt-5.4
    llm_plan LLM prompt construction + structured output All proposals agree
    decision_policy Post-LLM redirects, cap enforcement, calc adjustment gpt-5.4 (merged from opus's corrector chain)

    Key Design Rules (from gpt-5.4's anti-patterns section)¶

    1. Only tick increments iterations. No other node touches it.
    2. No state mutation in edge functions. Conditional edges are pure predicates.
    3. ask_user remains the single interrupt node. Gate nodes create decisions, they don't pause execution.
    4. One decision_policy node, not 5 corrector nodes. Splitting every redirect into its own node adds graph hops without improving clarity.
    5. Loop-back edges go to tick. Every iteration re-runs guards — this is correct and intentional.

    Migration Strategy (combined from gpt-5.4 + glm-5.1)¶

    1. Extract helpers without graph changes. Create _tick(), _bootstrap_gate(), _prepare_context(), _acquisition_gate(), _decision_policy() as pure functions called from plan_node. Tests pass unchanged.
    2. Add _build_plan_output() helper. Collapse the 9-way conditional return pattern (from glm-5.1).
    3. Wire tick into the graph first. START → tick → plan. Smallest checkpoint impact.
    4. Extract bootstrap_gate and prepare_context. Region/currency and schema prep move out of plan_node.
    5. Extract acquisition_gate and llm_plan. Deterministic routing separates from LLM call.
    6. Extract decision_policy. Post-LLM rewriting becomes the final normalization step.
    7. Delete plan_node. Clean up dead code, update docs.

    What NOT to do (consensus across proposals)¶

    • Don't move planner logic into the outer conversation graph.
    • Don't add AI slop footers or co-author trailers.
    • Don't split every if into its own node.
    • Don't mutate state in conditional edge functions.
    • Don't change PlannerDecision action names or PlannerSettings.
    • Don't change search backend behavior or calculator semantics.
