    Planner Graph Refactor Proposals — Analysis & Ranking¶

    Author: GLM-5.1 (Sisyphus analysis) Date: 2026-06-08 Scope: Evaluation of 10 proposals for decomposing plan_node (agent.py:846–1192, ~350 LOC)

    Summary of the Problem¶

    All 10 proposals target the same root issue: plan_node() is a ~350-line monolith mixing guard checks, deterministic routing, schema enrichment, LLM calls, and decision post-processing inside a single node. The graph's route_after_plan is trivially 4 lines (reads decision.action), meaning all real routing intelligence is invisible at the graph level.

    The proposals agree on the general direction — move deterministic logic to graph-level nodes and conditional edges — but differ substantially in granularity, naming, sequencing, and migration strategy.

    Ranked Proposals (Best → Worst)¶

    1. GPT-5.5 Proposal — Best Overall¶

    Node pipeline: enter_iteration → prepare_schema → require_region/require_currency → acquisition_gate → plan_llm → normalize_decision → retry_gate → maybe_calculate → dispatch

    Strengths:

    • Most thorough structural analysis. The proposal identifies 17 distinct concerns inside plan_node (lines 848–1192) and maps each to a specific node. This level of precision makes migration unambiguous.
    • Correct separation of normalize_decision (post-LLM correctors) from retry_gate (per-field caps). These are genuinely different concerns — one rewrites the type of decision, the other enforces attempt limits. Splitting them into separate nodes gives each a single responsibility and makes the retry policy visible in the graph.
    • maybe_calculate as a dedicated calculator-routing node is the right granularity. Calculator lifecycle management (finish→calculate rewrite, blocked→reflect) is a distinct policy concern that should not be mixed with per-field retry limits.
    • Delegates region/currency to dedicated nodes, not just conditional-edge dispatch from a gatekeep node. This makes the Mermaid diagram show the bootstrap question flow explicitly, which is valuable because these are interrupt() points visible to the user.
    • Explicit State additions are minimal and well-justified. Only llm_failed (or decision_origin) is proposed as a new field, with a clear explanation of why it's needed (preventing a failed LLM from entering reflect→plan_llm infinite loop via maybe_calculate).
    • Excellent migration plan (extract helpers → add nodes one group at a time → rename). Staged migration reduces risk because each group can be tested independently.
    • Clear "what should not change" section — explicitly rules out moving planner logic to the outer conversation graph, redesigning PlannerDecision action names, or changing search backend behavior. This prevents scope creep.

    Weaknesses:

    • 8 new pipeline nodes (enter_iteration, prepare_schema, require_region, require_currency, acquisition_gate, normalize_decision, retry_gate, maybe_calculate) plus the dispatch router. This is the second-most granular proposal. More nodes means more wiring, more conditional edges, and more state I/O — though each node is small and testable.
    • require_region and require_currency as separate nodes adds 2 interrupt-path nodes that each need their own observe handling. The proposal acknowledges this but doesn't detail how observe_user_node changes to route back to the correct re-entry point (currently observe_user sends back to plan/guard, not to require_region/require_currency).
    • No explicit treatment of route_reason for observability. The proposal mentions it as optional but doesn't recommend it, missing an opportunity to make LangSmith traces more useful.

    Verdict: The most complete and well-reasoned proposal. It correctly separates concerns at the right granularity: deterministic gates before LLM → LLM call → deterministic post-correction. The calculator lifecycle gets its own node, which is architecturally important because calculator-backed profiles have qualitatively different flow than search/ask profiles.

    2. DeepSeek-4-Pro Proposal — Strong Runner-Up¶

    Node pipeline: guard → prepare → plan → adjust → (action nodes)

    Strengths:

    • Balanced granularity. 4 new nodes (guard, prepare, plan, adjust) is the minimum viable decomposition. Each has a clear, single responsibility.
    • `adjust as a single post-LLM correction node is pragmatic. All five correction functions (_redirect_derived_direct_decision, _redirect_premature_ask_for_web_field, search caps, ask-user caps, _adjust_calculation_decision) are pure transformations on PlannerDecision — they don't need LLM calls and they're sequentially dependent. Keeping them in one node avoids 4–5 extra graph hops per iteration, each of which writes to the checkpointer.
    • Phase 1 "extract without changing topology" is the safest possible start. Mechanical extraction of helper functions with no behavioral change means zero regression risk for the first commit.
    • recipes in state is a pragmatic addition that eliminates redundant recomputation.
    • Good alternatives section. Explicitly considers and rejects 16-node decomposition, plan-conditional-edge-only approach, calculator subgraph, and minimal guard-only extraction — with clear reasoning for each.

    Weaknesses:

    • guard combines too many responsibilities. It handles iteration counting, abort/max_iters checks, region/currency bootstrapping, AND calculator-cap checks. The proposal says "~20 lines" for guard, but lines 846–943 (aborted + max_iters + region + currency + calc-cap + calc-success) is ~100 lines, not 20. The "20 lines" claim underestimates the function.
    • prepare mixes schema enrichment with acquisition gating. Lines 889–1035 include proactive decomposition, recipe building, field composition, calculator lifecycle checks, blocked-calculation acquisition, AND auto-finish detection. Calling this "~50 lines" is optimistic — the actual logic spans ~150 lines and covers 4 distinct concerns.
    • adjust combines cap enforcement with calculation adjustment. These are semantically different: cap enforcement is a policy guard (prevent infinite loops), while calculation adjustment is a flow redirect (finish→calculate). Merging them makes adjust responsible for both, which is exactly the "mixed concerns" problem the proposal argues against.
    • No maybe_calculate or retry_gate equivalent. Calculator lifecycle management and per-field retry limits are both inside adjust, making it harder to trace which policy triggered a route change.

    Verdict: The simplest viable decomposition. If the team values minimal graph changes and fast migration, this is a good choice. The 4-node pipeline is easy to understand and maintain. However, the lack of calculator-specific and retry-specific nodes means those policy concerns remain hidden in adjust, which partially undermines the "make routing visible at graph level" goal.

    3. Opus Proposal — Solid Architecture, Slightly Over-Decposed¶

    Node pipeline: g_iter_cap → g_region/emit_region → g_currency/emit_currency → enrich_schema → g_calc_caps/emit_calc_* → acquire → plan_llm → c_target_decompose → c_redirect_derived → c_redirect_web → c_search_cap → c_ask_cap → c_calc_adjust → dispatch

    Strengths:

    • Correct analysis deeply aligned with code. The line-number mapping (17 concerns mapped precisely) is the most detailed of all proposals. It makes the migration traceable.
    • c_* corrector chain is architecturally sound. Making each decision rewrite a separate node with add_edge (not add_conditional_edges) means the corrector chain is a linear pipeline — fast, no branching, each node writes only decision. This is the right approach for sequentially dependent transformations.
    • Gate/corrector/enrich naming convention (g_*, c_*, enrich) is clean and self-documenting.
    • Good trade-off analysis — honestly acknowledges more node hops, slight reader indirection, and multi-step migration risk.
    • Open questions are honest — acknowledges that enrich_schema always running may be wasteful, and asks whether acquire should be one or two nodes.

    Weaknesses:

    • 13 pipeline nodes + 5 action nodes = 18 total nodes. This is the most granular proposal. While each node is small and testable, the graph wiring is substantial. The Mermaid diagram becomes complex — which partially defeats the "make the graph readable" goal.
    • Separate emit_region/emit_currency nodes and emit_calc_abort/emit_calc_done nodes add extra hops for simple decision construction. These could be handled by the gate node emitting a decision plus a routing tag, rather than requiring a dedicated node per decision type.
    • g_region + emit_region as two separate nodes is over-decomposition. The predicate and the decision construction are tightly coupled — splitting them adds a graph hop for clarity that doesn't justify the complexity.
    • No explicit calculator routing node. Calculator adjustments happen inside c_calc_adjust, but there's no maybe_calculate that makes finish→calculate visible at graph level. This means the calculator lifecycle (which is qualitatively different from other corrections — it's not a redirect but a re-routing to a different action type) is still hidden inside a corrector.
    • Migration step 3 (split correctors) is low risk per the proposal, but in practice each c_* corrector depends on state that may have been mutated by the previous corrector. Splitting them into separate nodes means each gets its own checkpoint write, which increases latency and creates rollback risk if a corrector fails mid-chain.

    Verdict: Best naming convention and most detailed analysis. The 5-node corrector chain is architecturally pure but may be over-engineered for a production system. The enrich vs c_* vs g_* naming is worth adopting regardless of which proposal is chosen.

    4. GPT-5.4 Proposal — Well-Structured, Good Migration, Slightly Verbose Naming¶

    Node pipeline: tick → bootstrap_gate → prepare_context → acquisition_gate → llm_plan → decision_policy → (action nodes)

    Strengths:

    • Excellent anti-patterns section. "Do not move state mutation into edge functions" and "Do not increment iterations in every gate" are concrete, practical rules that prevent common LangGraph mistakes. This is the only proposal that explicitly warns against these pitfalls.
    • tick is the right abstraction for iteration management. Making iteration increment a dedicated entry node ensures it happens exactly once per loop, preventing subtle double-increment bugs.
    • decision_policy as a single post-LLM policy node is the pragmatic choice. It's what DeepSeek-4-Pro calls adjust — all corrections in one node. This avoids 5 extra graph hops per iteration while still making the policy visible as a named step.
    • Good naming choices: tick, bootstrap_gate, prepare_context, acquisition_gate, llm_plan, decision_policy are all self-documenting.
    • Staged migration (6 stages) is the most granular migration plan. Each stage is independently testable.

    Weaknesses:

    • 6 separate graph change stages is more overhead than necessary. Stages 3–6 (extract prepare_context, acquisition_gate, slim llm_plan, extract decision_policy) could be combined into 2 stages.
    • No explicit maybe_calculate node. Calculator routing is inside decision_policy, which means finish→calculate is hidden just like in the current code. This is a significant architectural shortcoming for calculator-backed profiles.
    • No retry_gate. Per-field search/ask caps are inside decision_policy, mixed with calculator adjustments. This makes the policy node carry two semantically different responsibilities.
    • bootstrap_gate combines region and currency questions but doesn't create dedicated interrupt nodes for them. The graph shows bootstrap_gate → ask_user but doesn't distinguish which bootstrap question triggered the interrupt, which reduces observability.
    • Verbose compared to DeepSeek-4-Pro (same 4-stage effective decomposition but with more documentation).

    Verdict: Strong on practical migration discipline and anti-pattern avoidance. The tick node and explicit anti-pattern rules are valuable contributions. Lacks the calculator-specific and retry-specific focus that GPT-5.5 provides.

    5. Kimi-2.6 Proposal — Good Structure, Naming Could Be Better¶

    Node pipeline: tick → ask_region/ask_currency → prepare → calc_gate → acquire → decide → enforce_policy → (action nodes)

    Strengths:

    • enforce_policy as a single post-LLM enforcement node is the same pragmatic choice as DeepSeek-4-Pro's adjust and GPT-5.4's decision_policy. Good.
    • Dedicated ask_region/ask_currency nodes — makes bootstrap questions visible in the graph diagram. This is architecturally correct even if it adds 2 nodes.
    • calc_gate as a separate node for calculator lifecycle checks. This separates calculator concerns from the acquisition/search pipeline, which is the right call for calculator-backed profiles.
    • route_direct node — a tiny adapter that bridges deterministic acquisition tasks into the same post-processing pipeline as LLM decisions. This is a good pattern for keeping the enforcement pipeline unified.
    • Excellent decision matrix appendix — maps each logic block to its proposed location with a "Reason" column. Very useful for implementation.
    • Phased migration is well-structured (extract helpers → register as nodes → delete old code).

    Weaknesses:

    • acquire combines blocked-calc acquisition AND generic acquisition with auto-finish logic. This is 3 concerns in one node, which partially undermines the "one node one job" principle.
    • No maybe_calculate equivalent. Calculator adjustments (_adjust_calculation_decision) are inside enforce_policy, mixed with cap enforcement.
    • tick routes to ask_region/ask_currency/prepare — this means iteration increment happens before bootstrap questions, which is correct but differs from DeepSeek-4-Pro where guard handles both. The approach is fine but the routing from tick is 5-way (aborted | max_iters | ask_region | ask_currency | ready), which is a lot for one conditional edge.
    • Naming is functional but not self-documenting. tick, acquire, decide, enforce_policy are passable but less descriptive than GPT-5.4's tick/bootstrap_gate/prepare_context/acquisition_gate/llm_plan/decision_policy.

    Verdict: Solid middle-ground proposal. The separate calc_gate is a good addition that DeepSeek-4-Pro lacks. The route_direct pattern is elegant. But the lack of calculator-specific routing and the overloaded acquire node keep it behind GPT-5.5 and DeepSeek-4-Pro.

    6. GLM-5.1 Proposal (this model's own proposal) — Pragmatic Two-Node Split¶

    Node pipeline: pre_check → acquire_or_plan → (action nodes)

    Strengths:

    • Simplest proposal that still solves the core problem. Only 2 new nodes (pre_check + renamed acquire_or_plan) plus routing functions.
    • Option A (keep post-LLM rewriting in acquire_or_plan) is the safest first-pass choice. It avoids adding graph hops for what are pure transformations on a single PlannerDecision object.
    • Option B (extract validate_decision) is left as a future improvement — good incremental approach.
    • _build_plan_output helper to collapse the 9 conditional-return pattern is a nice code quality improvement that doesn't require graph changes.
    • Good risk section — identifies checkpoint compatibility, state snapshot consistency, and dynamic decomposition ordering as real concerns.

    Weaknesses:

    • pre_check is too large. It handles iteration increment, abort/max_iters, region, currency, proactive decomposition, composition, calculator cap exhaustion, AND calculator success detection. That's 8 concerns in one node (~150 LOC), which is still a monolith, just smaller than the original 350-line one.
    • acquire_or_plan is still ~200 lines per the proposal's own estimate. It owns acquisition, LLM call, auto-finish, and all post-LLM rewriting. This is better than the original but still carries 7 distinct responsibilities.
    • No separation of calculator lifecycle from acquisition. The calculator cap/success checks are in pre_check, but _adjust_calculation_decision stays in acquire_or_plan. This means calculator policy is split across two nodes, making it harder to reason about.
    • No retry gate or cap enforcement node. Search/ask caps and the finish→calculate rewrite are all inside acquire_or_plan, which is exactly the "hidden routing" problem the proposal identifies.
    • _pre_check_route state field uses string-typed literals, which is less type-safe than the enum-based Action extension the proposal mentions as an alternative.

    Verdict: The safest minimal change, but it only solves ~60% of the problem. The pre_check node is still too large, and acquire_or_plan still mixes too many concerns. Best used as a Phase 1 stepping stone toward a deeper refactoring, not as the end state.

    7. Gemini-3.1-Pro Proposal — Correct Direction, Under-Specified¶

    Node pipeline: prepare_state → evaluate_rules → llm_plan → (action nodes)

    Strengths:

    • Correctly identifies the core issue — hidden control flow, mixed concerns, hard testing.
    • prepare_state as pure state mutation separate from evaluate_rules as pure routing is a clean separation.
    • Simple 3-node split is easy to implement and understand.

    Weaknesses:

    • Missing calculator-specific handling. No calc_gate, no maybe_calculate, no calculator lifecycle node. Calculator-backed profiles have fundamentally different flow, and this proposal ignores that.
    • evaluate_rules combines too much. It handles aborted/max_iters, region/currency, calculator status, blocked calc acquisition, and auto-finish. This is the same problem as the original plan_node — just in a different function.
    • No adjust/decision_policy/enforce_policy node. All post-LLM corrections are implicitly inside llm_plan, which means the graph diagram still hides decision rewriting.
    • No migration plan — just "1. Refactor functions, 2. Update edges, 3. Rebuild graph." No phases, no testing strategy, no risk assessment.
    • No risk analysis, no alternatives considered, no state schema discussion.

    Verdict: Directionally correct but substantially under-specified compared to other proposals. Lacks calculator handling, post-LLM correction separation, migration strategy, and risk analysis. Only suitable as a rough starting point, not as an implementation plan.

    8. Mimo-2.5-Pro Proposal — Clean 3-Node Split, Missing Key Details¶

    Node pipeline: guards → acquire → decide → (action nodes)

    Strengths:

    • 3 nodes is the simplest meaningful decomposition. guards for deterministic gating, acquire for state preparation + task selection, decide for LLM + post-processing.
    • Good expected benefits table — concrete LOC estimates, branching depth, testability, debuggability improvements.
    • Phased migration (extract → wire → cleanup) is practical.
    • Good risk table — state key compatibility, interrupt preservation, hidden coupling.

    Weaknesses:

    • guards combines 6 concerns (iteration, abort, max_iters, region, currency, calculator status) into ~40 lines. The "40 lines" estimate is unrealistic — the actual logic spans ~100 lines.
    • decide still owns all post-LLM corrections including acquisition task resolution, derived-field redirects, web-preferred redirects, search caps, ask-user caps, and calculation adjustments. This is ~80 lines with 6 responsibilities.
    • No calculator-specific node. Calculator lifecycle is inside guards (cap/success), but _adjust_calculation_decision is inside decide. Split calculator policy across two nodes.
    • Open questions are left unanswered — should decide include loop/cap detection, or should that be a separate validate_decision? The proposal doesn't take a position.
    • plan_router as an intermediate routing construct adds complexity without clear benefit. It's just route_after_plan by another name.

    Verdict: Similar in spirit to GLM-5.1's two-node split but with better documentation. The 3-node split (guards/acquire/decide) is cleaner but still leaves decide as a multi-concern function. Good as a stepping stone, not as an end state.

    9. Qwen-3.6-Plus Proposal — Over-Ambitious, Introduces New Concepts¶

    Node pipeline: preflight → ask_region/ask_currency → observe_region/observe_currency → decompose → plan → (action nodes)

    Strengths:

    • Dedicated observe_region/observe_currency nodes — properly separates region/currency answer handling from observe_user. This is architecturally cleaner than all other proposals.
    • route_finish_check as a separate node — makes auto-finish logic visible at graph level. Good.
    • Moves post-LLM redirects to route_after_plan routing function — makes them visible in the graph. This is the only proposal that makes redirects an explicit routing concern rather than hiding them in a post-LLM node.

    Weaknesses:

    • Introduces observe_region/observe_currency as entirely new nodes — this requires splitting _handle_region_answer and _handle_currency_answer out of observe_user_node, which is additional work beyond just decomposing plan_node. The proposal conflates decomposing plan_node with refactoring observe_user_node.
    • route_after_plan becomes a complex routing function with 6 conditional branches (derived redirect, web-preferred redirect, calculator redirect, search cap, ask-user cap). Routing functions should be simple predicates — not policy engines. Putting this logic in an edge function means it can't log, emit events, or produce side effects.
    • preflight combines iteration, abort, max_iters, region, currency, calculator cap, AND calculator success — this is 7 concerns in one node, making it larger than the original plan_node gate section it replaces.
    • No dedicated acquisition gate. The proposal skips from decompose to plan, losing the deterministic acquisition path that calculator-backed profiles rely on.
    • No enforce_caps or retry_gate. Cap enforcement is in the routing function, which means it's invisible in LangSmith traces and can't be unit-tested as a node.
    • Observation loop-back issue: observe_region → preflight and observe_currency → preflight means region/currency questions go through the full pre-flight check again, including proactive decomposition and calculator status — which is wasteful for a simple region/currency answer.

    Verdict: Creative but introduces unnecessary new concepts (observe_region/observe_currency nodes) and puts too much policy in routing functions. The route_after_plan with 6 conditional branches is actually worse than the current route_after_plan (4 lines) because it hides policy in a non-node, non-loggable, non-testable place.

    10. Qwen-3.7-Max Proposal — Most Granular, Produces Pseudo-Code But Over-Engineered¶

    Node pipeline: check_termination → check_region_currency → compose_schema → check_calculator → acquisition_routing → check_completion → llm_decide → post_process → enforce_caps → route_decision → (action nodes)

    Strengths:

    • Most detailed implementation code. Every node has a full Python implementation with specific state handling. This is useful as a reference for implementers.
    • enforce_caps as a dedicated node — makes per-field retry limits visible at graph level.
    • Minimal state additions — _route and _llm_failed transient fields with clear semantics.
    • check_termination completely isolated — iteration management is its own node, which is correct.

    Weaknesses:

    • 10 new pipeline nodes (not counting action nodes) makes this the most complex graph. The Mermaid diagram has 15+ nodes and 20+ edges. This level of granularity makes the graph harder to read than the original monolith.
    • _route transient state field used for inter-node routing. This is an anti-pattern in LangGraph — conditional edges should read state and compute routes, not pass routing hints through state. Using _route means nodes are writing routing metadata that has nothing to do with business state, which pollutes the state schema and makes checkpoint debugging harder.
    • check_calculator with multiple routing labels (finish | blocked | pending | no_calc) — fine-grained routing but the labels are implementation details, not meaningful flow names.
    • acquisition_routing contains dynamic decomposition generation (lines 265-287 in the proposal). This means the acquisition node can call _llm() for decomposition, which is an LLM call inside a "deterministic" node. This contradicts the stated principle of separating LLM concerns.
    • enforce_caps calls next_acquisition_task() and _decision_from_acquisition_task() — these are side effects inside what should be a pure cap-enforcement node. This mixes policy enforcement with task resolution.
    • No migration phases — just 5 unnamed phases with no testing strategy or risk assessment.
    • check_completion contains acquisition logic — _decision_from_acquisition_task is called inside what should be a simple "all fields collected?" check.

    Verdict: Over-engineered. The 10-node pipeline is too granular for production use. The _route state field is a LangGraph anti-pattern. The pseudo-code is useful as reference but should not be implemented as-is. Several nodes (acquisition_routing, check_completion, enforce_caps) contain logic that contradicts their stated single responsibility.

    Conclusion & Recommendation¶

    Recommended Approach: GPT-5.5 as Base + Selective Borrowing¶

    GPT-5.5's proposal is the strongest foundation for implementation, with the following borrowings from other proposals:

    1. From Opus: The g_*/c_*/enrich naming convention. Using prefixes like gate_, correct_, enrich_ or g_/c_ makes node purpose immediately clear in the Mermaid diagram and in code. Adopt gate_ for gate nodes, enrich_ for state transformation, and correct_ for post-LLM policy corrections.

    2. From DeepSeek-4-Pro: The adjust pattern as an initial state for post-LLM corrections. Start with a single correct_policy node (DeepSeek's adjust) containing all five corrections. Only split into separate nodes if testing reveals it's still too complex. This reduces migration risk and avoids 5 extra graph hops per iteration.

    3. From GPT-5.4: The anti-pattern rules. Explicitly document: "Do not mutate state in edge functions", "Only tick/enter_iteration writes iterations", "Do not turn every policy rule into a node", "Do not move interrupts into policy gates."

    4. From Kimi-2.6: The route_direct pattern for acquisition tasks. When acquisition_gate produces a deterministic decision, route it directly through correct_policy (skipping plan_llm), not through a separate path. This keeps the post-correction pipeline unified.

    This preserves: - Calculator lifecycle as a visible gate (gate_calculator) - Bootstrap questions as a visible gate (gate_bootstrap) - Iteration management as a single entry point (enter_iteration) - Post-LLM policy as a unified correction node (correct_policy) - Acquisition path that bypasses the LLM when deterministic - Enrichment as a pure state transformation (enrich_schema)
