    Planner Graph Refactor Proposals — Ranked Evaluation¶

    Evaluator: Sisyphus (mimo-v2.5-pro) Date: 2026-06-08 Scope: All 10 proposals in docs/planner-graph-ref/proposals/

    Shared Diagnosis¶

    Every proposal correctly identifies the same root problem: plan_node (agent.py:846-1192) is a ~350-line monolith that conflates:

    • Iteration guards and early exits
    • Region/currency bootstrap questions
    • Schema decomposition and composition
    • Calculator lifecycle gating
    • Deterministic acquisition routing
    • LLM decision generation
    • Post-LLM decision correction (redirects, caps, calculation adjustment)

    The consequence: route_after_plan is a trivial 4-line function (return decision.action), meaning the graph has zero routing intelligence — all orchestration is hidden inside the node.

    Ranking¶

    1. Deepseek V4 Pro — deepseek-4-pro-proposal.md¶

    Score: 9/10

    Architecture: 4-node pipeline: guard → prepare → plan → adjust

    Aspect Assessment
    Node count 4 new nodes (8→11 total). Sweet spot — enough granularity without graph explosion.
    Separation of concerns Excellent. Guard (early exits), Prepare (schema enrichment), Plan (LLM only), Adjust (post-LLM correction). Each has a single, clear contract.
    Post-LLM handling Dedicated adjust node. This is the only proposal that cleanly isolates all post-LLM correction into its own node without making it too granular.
    Loop-back edges Returns to guard — semantically correct since guard checks abort/max_iters every iteration.
    State changes Minimal: adds recipes to state (already computed in 2 places). Sensible deduplication.
    Migration path 4-phase, mechanical extraction at each step. Tests pass at each phase. Lowest-risk migration of all proposals.
    Trade-off analysis Honest and complete. Acknowledges more hops per iteration, more routing functions, but correctly notes each is trivial.

    Strengths: - The prepare → plan → adjust pipeline is the cleanest decomposition of the "enrich → decide → correct" pattern. - adjust as a pure transformation node (no LLM, only decision rewriting) is architecturally sound. - The self-loop in plan for decomposition generation is clever — handles the "LLM targets composite field" case without extra nodes. - Phase 1 (extract helpers, no graph change) is the safest possible first step.

    Weaknesses: - prepare node still does a lot (~50 lines of schema composition + calculator checks). Could be split further, but the proposal correctly argues against over-decomposition. - The guard re-entry from action nodes changes the loop-back target from plan to guard, which requires careful checkpointer testing.

    2. GPT-5.4 — gpt-5.4-proposal.md¶

    Score: 8.5/10

    Architecture: 5-node pipeline: tick → bootstrap_gate → prepare_context → acquisition_gate → llm_plan + decision_policy

    Aspect Assessment
    Node count 5 new nodes + 1 policy node (8→13 total). Slightly more granular than Deepseek.
    Separation of concerns Excellent. The split between tick (iteration lifecycle), bootstrap_gate (region/currency), prepare_context (schema enrichment), and acquisition_gate (deterministic routing) is well-motivated.
    Post-LLM handling decision_policy node — correct approach. Keeps all post-LLM normalization in one place.
    Loop-back edges Returns to tick — correct, ensures iteration counting happens exactly once per loop.
    Migration path Best migration plan of all proposals. 6 stages, each independently shippable, with clear test verification at each stage.
    Anti-pattern warnings Explicit warnings against state mutation in edge functions, incrementing iterations in multiple gates, and turning every policy rule into a node. Shows deep LangGraph understanding.

    Strengths: - The "deterministic orchestration belongs in graph phases; business logic stays in helpers; LLM planning stays small" principle is the clearest articulation of the design philosophy. - tick as a dedicated iteration-lifecycle node is a better name and contract than Deepseek's guard (which also handles region/currency). - acquisition_gate cleanly separates "what to do next" from "how to do it" — the calculator/acquisition routing doesn't pollute the LLM path. - The staged migration (6 stages) is more granular than Deepseek's 4 phases, reducing risk per PR.

    Weaknesses: - decision_policy is still ~80 lines and bundles 5 different correction concerns. Could be split, but the proposal correctly argues against it. - More nodes than Deepseek (13 vs 11) with marginal benefit — the extra split between tick and bootstrap_gate adds a hop but doesn't significantly improve testability over Deepseek's guard.

    3. GLM-5.1 — glm-5.1-proposal.md¶

    Score: 8/10

    Architecture: 2-node split: pre_check → acquire_or_plan

    Aspect Assessment
    Node count 2 new nodes (8→10 total). Minimal graph change.
    Separation of concerns Good but incomplete. pre_check handles guards + prerequisites + preprocessing. acquire_or_plan handles acquisition + LLM + post-LLM rewriting.
    Post-LLM handling Kept inside acquire_or_plan for Phase 1, with explicit Option B (validate_decision node) for later. Pragmatic.
    Migration path 4 phases, well-sequenced. Phase 1 extracts pre_check, Phase 2 renames plan → acquire_or_plan, Phase 3 extracts _build_plan_output helper, Phase 4 optionally extracts validate_decision.
    State changes Minimal: _pre_check_route field or extended Action enum.

    Strengths: - Lowest-risk proposal. Only 2 new nodes means minimal graph topology change, minimal checkpointer impact. - The phased approach (extract pre_check first, rename later, optionally split further) is the most conservative and safest path. - _build_plan_output helper to collapse the 9-way conditional-return pattern is a valuable standalone improvement regardless of graph changes. - The explicit acknowledgment that post-LLM rewriting could be a separate node but shouldn't be yet shows good engineering judgment.

    Weaknesses: - acquire_or_plan is still ~200 lines after extraction — it bundles acquisition, LLM call, and post-LLM correction. This is the proposal's main limitation. - Doesn't solve the "graph has no routing intelligence" problem as thoroughly as Deepseek or GPT-5.4. - The _pre_check_route state field adds a transient routing hint to state, which is a minor anti-pattern (routing should be in edge functions, not state).

    4. Kimi K2.6 — kimi-2.6-proposal.md¶

    Score: 7.5/10

    Architecture: 8-node pipeline: tick → prepare → calc_gate → acquire → decide → enforce_policy

    Aspect Assessment
    Node count 8 new nodes (8→15 total). More granular than Deepseek.
    Separation of concerns Good. The tick/prepare/calc_gate/acquire/decide/enforce_policy chain is well-motivated.
    Post-LLM handling enforce_policy node — correct approach, bundles all post-LLM correction.
    Decision matrix Excellent appendix. The "Decision Matrix (What Goes Where)" table is the clearest mapping of old logic to new nodes across all proposals.
    Naming Clean, consistent naming. tick, prepare, calc_gate, acquire, decide, enforce_policy — each name accurately describes the node's contract.

    Strengths: - The decision matrix is a standout feature — it makes the proposal immediately actionable for implementation. - ask_region / ask_currency as dedicated nodes (not routing through generic ask_user) makes bootstrap questions structurally visible. - route_direct as a tiny adapter node bridging deterministic acquisition tasks into the post-processing pipeline is a clean pattern. - The migration path (extract helpers → register as nodes → delete plan_node) is straightforward.

    Weaknesses: - ask_region / ask_currency as separate nodes adds unnecessary complexity. They follow the same pattern (produce a PlannerDecision, route to ask_user) and could be a single bootstrap node with conditional routing. - 15 total nodes is on the high side for a planner subgraph. Each node adds a checkpointer write. - The proposal doesn't discuss the loop-back edge change (should action nodes return to tick or plan?) — a significant gap.

    5. GPT-5.5 — gpt-5.5-proposal.md¶

    Score: 7.5/10

    Architecture: 8-node pipeline: enter_iteration → prepare_schema → require_region/require_currency → acquisition_gate → plan → normalize_decision → retry_gate → maybe_calculate

    Aspect Assessment
    Node count 8 new nodes (8→15 total). Same as Kimi.
    Separation of concerns Very granular. Splits post-LLM correction into normalize_decision (redirects), retry_gate (caps), and maybe_calculate (calculator adjustment).
    State changes Recommends llm_failed: bool or decision_origin field. Sensible for calculator routing.
    Non-goals Explicitly lists what stays unchanged. Good scope control.

    Strengths: - The most thorough analysis of consequences (positive and negative). Every trade-off is explicitly listed. - normalize_decision / retry_gate / maybe_calculate split makes each correction independently testable. - The "keep these responsibilities out of the outer conversation graph" section prevents scope creep. - The staged migration with "preserve existing public graph surface" at each step is disciplined.

    Weaknesses: - Over-decomposed. 8 new nodes for a 350-line function is excessive. The split between normalize_decision, retry_gate, and maybe_calculate adds 3 nodes where 1 (decision_policy) would suffice. - require_region / require_currency as separate nodes (same criticism as Kimi). - The graph diagram is hard to read due to the number of nodes and edges. - Migration risk is higher because more nodes = more edge predicates = more places for bugs.

    6. Gemini 3.1 Pro — gemini-3.1-pro-proposal.md¶

    Score: 7/10

    Architecture: 3-node split: prepare_state → evaluate_rules → llm_plan

    Aspect Assessment
    Node count 3 new nodes (8→11 total).
    Separation of concerns Clean but incomplete. prepare_state (schema mutation), evaluate_rules (deterministic routing), llm_plan (LLM call).
    Post-LLM handling Not addressed. Post-LLM redirects stay inside llm_plan, which defeats the purpose of the refactor.
    Brevity Shortest proposal (117 lines). Easy to review.

    Strengths: - The 3-node split is the simplest possible decomposition that still moves logic to the graph level. - evaluate_rules as a deterministic routing node that returns either a PlannerDecision or None (needs LLM) is a clean pattern. - The proposal correctly identifies that the LLM node should be isolated to prevent unintentional invocation.

    Weaknesses: - Post-LLM handling is a critical gap. The proposal doesn't address the 70+ lines of post-LLM correction (derived redirects, web-preferred redirects, search caps, ask caps, calculation adjustment). These stay buried in llm_plan. - evaluate_rules bundles too many concerns (max_iters, region/currency, calculator status, acquisition routing, auto-finish) into one node — it's essentially the same monolith with a different name. - No migration path — the proposal jumps straight to the target architecture without explaining how to get there safely.

    7. Qwen 3.6 Plus — qwen-3.6-plus-proposal.md¶

    Score: 7/10

    Architecture: 7-node split: preflight → decompose → plan + route_after_plan (with redirects) + route_finish_check

    Aspect Assessment
    Node count 7 new nodes (8→14 total).
    Separation of concerns Good. preflight (guards), decompose (schema enrichment), plan (LLM only), route_finish_check (auto-finish validation).
    Post-LLM handling Moves redirects into route_after_plan (the routing function). This is a problem — routing functions should be pure predicates, not side-effectful transformers.
    Migration path 5 phases, well-structured.

    Strengths: - route_finish_check as a dedicated node for auto-finish validation is a good idea — it catches the case where finish is inappropriate (missing fields still exist). - The ask_region / ask_currency → observe_region / observe_currency loop is explicit and testable. - The "What Changes vs What Stays" table is clear and actionable.

    Weaknesses: - Moving redirects into route_after_plan is an anti-pattern. Routing functions in LangGraph should inspect state and return a route label — they should not mutate decision. This makes the graph harder to reason about and violates LangGraph's design contract. - observe_region / observe_currency as separate nodes (same criticism as Kimi/GPT-5.5) — they're just observe_user_node with a different target field. - The proposal acknowledges this in its Open Questions but doesn't resolve it.

    8. MiMo 2.5 Pro — mimo-2.5-pro-proposal.md¶

    Score: 6.5/10

    Architecture: 3-node split: guards → acquire → decide

    Aspect Assessment
    Node count 3 new nodes (8→11 total).
    Separation of concerns Adequate but incomplete. guards (early exits + region/currency), acquire (decomposition + acquisition), decide (LLM + post-LLM).
    Post-LLM handling Bundled inside decide — same problem as Gemini.
    Open questions Honestly raises 3 open questions (validate_decision split, plan_router node vs function, naming).

    Strengths: - The 3-node split is simple and easy to understand. - The migration path (Phase 1: extract without changing topology, Phase 2: wire into graph, Phase 3: cleanup) is sound. - The open questions section shows intellectual honesty — the proposal acknowledges its own gaps.

    Weaknesses: - decide bundles LLM call + post-LLM correction + loop/cap detection. It's still ~120 lines — not a significant improvement over the current plan_node. - The proposal doesn't address loop-back edges (should action nodes return to guards or decide?). - The plan_router node (line 166) adds unnecessary indirection — it's just a routing function pretending to be a node.

    9. Opus — opus-proposal.md¶

    Score: 6/10

    Architecture: 16-node pipeline: g_iter_cap → g_region → emit_region → g_currency → emit_currency → enrich_schema → g_calc_caps → emit_calc_abort/emit_calc_done → acquire → emit_acq/emit_auto_finish → plan_llm → c_target_decompose → c_redirect_derived → c_redirect_web → c_search_cap → c_ask_cap → c_calc_adjust → dispatch

    Aspect Assessment
    Node count 16 new nodes (8→23 total). Severely over-decomposed.
    Separation of concerns Each node is trivially small (10-30 lines). Perfect single-responsibility, but at the cost of graph complexity.
    Post-LLM handling Each corrector is its own node. Maximum testability, maximum graph noise.
    Migration path 3-step, each step ships green tests. Well-structured.

    Strengths: - The g_* / enrich / acquire / plan_llm / c_* / dispatch naming convention is the most systematic of all proposals. - The "one invariant ties everything together" section (every path deposits a PlannerDecision into state["decision"]) is a clean architectural contract. - The 3-step migration is disciplined and each step is independently shippable. - The checkpoint footprint analysis (each node writes only the fields it owns) is unique and valuable.

    Weaknesses: - 23 total nodes is excessive. A planner subgraph with 23 nodes is harder to read, harder to debug, and incurs significant checkpointer overhead (each node = 1 postgres write). - emit_region / emit_currency / emit_calc_abort / emit_calc_done / emit_acq / emit_auto_finish are all single-purpose "emit decision" nodes that could be merged. - The corrector chain (c_target_decompose → c_redirect_derived → c_redirect_web → c_search_cap → c_ask_cap → c_calc_adjust) adds 6 sequential hops per iteration. The proposal acknowledges this but underestimates the impact. - The Mermaid diagram is unreadable due to node count.

    10. Qwen 3.7 Max — qwen-3.7-max-proposal.md¶

    Score: 5.5/10

    Architecture: 10-node split: check_termination → check_region_currency → compose_schema → check_calculator → acquisition_routing → check_completion → llm_decide → post_process → enforce_caps → route_decision

    Aspect Assessment
    Node count 10 new nodes (8→18 total).
    Separation of concerns Each node has a clear contract, but the naming is inconsistent (check_*, compose_*, acquisition_*, llm_*, post_*, enforce_*, route_*).
    Post-LLM handling Split into post_process (redirects) and enforce_caps (caps). Correct separation.
    State changes Adds _route and _llm_failed transient fields. Problematic — _route duplicates the routing function's job.
    Code examples Most verbose proposal (722 lines). Includes full function implementations for every node.

    Strengths: - Full code examples make the proposal immediately implementable. - The post_process / enforce_caps split is correct — redirects and caps are different concerns. - The _llm_failed flag is a sensible addition for calculator routing.

    Weaknesses: - _route state field is an anti-pattern. It duplicates what routing functions should do. The proposal uses state.get("_route", "continue") in routing functions, which means state mutation determines routing — this is backwards. - check_region_currency bundles region and currency into one node but routes to ask_region / ask_currency as separate nodes (inconsistent with Kimi/GPT-5.5 which split them). - observe_user is shared between ask_region, ask_currency, and ask_user — the routing function needs to distinguish between them, which adds complexity. - The graph construction code (lines 550-672) is the most verbose of all proposals and hard to review. - compose_schema → check_calculator → acquisition_routing → check_completion → llm_decide is 5 sequential hops before the LLM even runs. Excessive.

    Recommendation¶

    Best Single Proposal: Deepseek V4 Pro¶

    The Deepseek proposal strikes the optimal balance between: - Graph readability (4 new nodes, each with a clear contract) - Testability (each node is independently testable) - Migration safety (4-phase, mechanical extraction) - Post-LLM handling (dedicated adjust node)

    Best Combination: Deepseek V4 Pro + GPT-5.4 Migration + GLM-5.1 Helper¶

    Combine:

    1. Graph structure from Deepseek (guard → prepare → plan → adjust) — the 4-node pipeline is the cleanest decomposition.
    2. Migration strategy from GPT-5.4 — the 6-stage migration is more granular and safer than Deepseek's 4-phase approach.
    3. _build_plan_output helper from GLM-5.1 — the helper to collapse the 9-way conditional-return pattern is a valuable standalone improvement that should be extracted in Stage 1 regardless of graph changes.

    Specific Adjustments to the Combined Approach¶

    1. Rename Deepseek's guard to tick (from GPT-5.4) — tick better describes the iteration-lifecycle contract.
    2. Keep Deepseek's prepare as-is — it bundles schema enrichment + calculator checks, which is acceptable for a ~50-line node.
    3. Keep Deepseek's plan as-is — the self-loop for decomposition generation is clever and correct.
    4. Keep Deepseek's adjust as-is — the dedicated post-LLM correction node is the strongest differentiator.
    5. Add GPT-5.4's anti-pattern warnings to the migration plan — especially "do not move state mutation into edge functions" and "do not increment iterations in every gate."
    6. Extract GLM-5.1's _build_plan_output helper in Stage 1 (before any graph changes) to simplify the 9-way conditional-return pattern in the current plan_node.

    What to Avoid¶

    1. Over-decomposition (Opus, Qwen 3.7 Max) — 16-23 nodes adds checkpointer overhead and makes the graph unreadable.
    2. Routing via state fields (Qwen 3.7 Max's _route) — routing should happen in edge functions, not state.
    3. Redirects in routing functions (Qwen 3.6 Plus) — routing functions should be pure predicates, not side-effectful transformers.
    4. Separate ask_region / ask_currency nodes (Kimi, GPT-5.5, Qwen 3.6 Plus) — they follow the same pattern and should be a single bootstrap concern inside guard/tick.

    Conclusion¶

    The Deepseek V4 Pro proposal is the strongest standalone proposal. Its 4-node pipeline (guard → prepare → plan → adjust) is the optimal granularity for a 350-line monolith — enough decomposition to make each node testable and readable, but not so much that the graph becomes noisy.

    The recommended approach is to adopt Deepseek's graph structure, use GPT-5.4's staged migration strategy, and extract GLM-5.1's _build_plan_output helper as a prerequisite improvement. This combination minimizes migration risk while maximizing the architectural improvement.
